What triage found
#119 webpack-dev-server vulnerable to HMR WebSocket interception via permissive user proxies — webpack-dev-server 4.15.2 is in range (<5.2.5) and the vulnerable code runs every time a developer executes `npm start` (package.json:75), so I cannot mark it not_used. Unlike the other dev-only alerts here, the impact is not DoS or Windows-specific: HMR WebSocket interception can exfiltrate project source from a developer's machine if they visit a hostile page with the dev server running. Accepting that is a team call, not mine, so this fails closed. I could not fully rule out reachability on the 'permissive user proxies' precondition either: we set no dev-server proxy, but the advisory does not state that a proxy is strictly required. Recommended: Bump webpack-dev-server to >=5.2.5. This IS a breaking change for us: react-scripts 5.0.1 pins webpack-dev-server ^4.6.0, so it cannot be satisfied by a plain install — it needs an npm `overrides` entry in package.json (none exists today) plus validation of the v4→v5 dev-server config/API changes under craco. Interim mitigation: do not run `npm start` while browsing untrusted sites. 
https://github.com/teqplay/terminal-planner/security/dependabot/119
#107 webpack-dev-server vulnerable to cross-origin source code exposure on non-HTTPS origins — webpack-dev-server@4.15.2 is within the vulnerable range (<=5.2.3) and the vulnerable path is actually exercised: `npm start` runs `craco start`, which starts this dev server over plain HTTP on localhost. The advisory's cross-origin source-code exposure on non-HTTPS origins means a malicious site visited by a developer while the dev server runs can read this proprietary frontend's source. Although dev-only and not deployed, the impact is a real confidentiality loss of commercial source code, so calling it acceptable is a judgment for the team rather than a documented non-issue. Failing closed. Recommended: Bump webpack-dev-server to 5.2.4. This IS breaking for us: react-scripts@5.0.1 declares webpack-dev-server ^4.6.0, so 5.x requires a forced npm `overrides` entry against an incompatible v5 API, or migration off react-scripts (CRA is unmaintained) to Vite. Interim mitigation: serve the dev server over HTTPS or bind it to 127.0.0.1. 
https://github.com/teqplay/terminal-planner/security/dependabot/107
#101 lodash vulnerable to Prototype Pollution via array path bypass in `_.unset` and `_.omit` — lodash-es@4.17.21 is in the vulnerable range (<=4.17.23) and is a RUNTIME dependency that ships in the production bundle. Our own code is clean: src/ contains zero lodash-es imports, and no _.unset/_.omit/_.omitBy call anywhere. However, the advisory requires checking the intermediate package, and its sole consumer is react-leaflet@1.9.1, whose source I could not inspect: node_modules is not installed and fetching the published tarball was blocked (no writable path outside the repo, and network file fetches were denied). Because I cannot show react-leaflet never calls the vulnerable APIs with a caller-supplied path, and this code ships to production, I am failing closed rather than guessing. Recommended: Bump lodash-es to 4.18.0+ (4.18.1 available). This is NOT breaking for us: react-leaflet@1.9.1 declares lodash-es ^4.0.0, which already permits 4.18.1, so a lockfile refresh fixes it with no manifest change. Re-run the triage after `npm install` to confirm reachability if the bump is deferred. 
https://github.com/teqplay/terminal-planner/security/dependabot/101
#58 Lodash has Prototype Pollution Vulnerability in `_.unset` and `_.omit` functions — Fail-closed: lodash-es 4.17.21 is a RUNTIME dependency that ships. Its lockfile entry has no dev:true flag, and its only parent, react-leaflet 1.9.1, is a production dependency that src/ actually imports in three components. I could not establish that react-leaflet never calls unset/omit: node_modules is not installed and fetching the package source (npm pack) was denied in this read-only session, so no grep of the intermediate was possible. Tree-shaking may drop it, but that is inference, not evidence. Recommended: Bump lodash-es to 4.17.23. react-leaflet declares lodash-es ^4.0.0 (package-lock.json:17620), so 4.17.23 satisfies the existing range - this is a lockfile-only semver-patch bump and is NOT a breaking change for us.

#57 Lodash has Prototype Pollution Vulnerability in `_.unset` and `_.omit` functions — Fail-closed: lodash 4.17.21 is a direct RUNTIME dependency (no dev:true in the lockfile) that ships in the production bundle. Our own code is clean - a grep for omit/omitBy/unset across src/ matched only CSS `unset` values, which covers the wildcard `import _ from 'lodash'` sites too. However, the same hoisted lodash is shared by shipped transitive consumers (recharts, react-smooth, react-color, reactcss, @teqplay/web-sdk), and I could not grep them because node_modules is absent and fetching sources was denied. Without that evidence the vulnerable path cannot be ruled out. Recommended: Bump lodash to 4.17.23 in package.json dependencies. This is a semver-patch bump within 4.17.x and is NOT a breaking change for us.

#44 webpack-dev-server users' source code may be stolen when they access a malicious web site with non-Chromium based browser — This one is genuinely reachable. webpack-dev-server 4.15.2 is dev-only, but 'dev-only' is not the same as unreachable: package.json scripts.start runs craco start, which boots this dev server on developer machines. The advisory's scenario - a developer running the dev server who visits a malicious site in a non-Chromium browser can have their source code exfiltrated - applies directly, and the payload is the proprietary source of this planner. There is no config here that mitigates it, so it cannot be dismissed as not_used, and source-code theft is not an impact I would call tolerable on this repo's behalf. Recommended: Bump webpack-dev-server to 5.2.1 or later. This IS a breaking change for us: react-scripts 5.0.1 declares webpack-dev-server ^4.6.0 (package-lock.json:17884), so v5 cannot be reached by a lockfile bump - it needs an npm `overrides` entry forcing v5 across the react-scripts tree (with v5's breaking config changes, e.g. server/https and devMiddleware options), or migrating off react-scripts. Interim mitigation: develop against a Chromium-based browser, which the advisory notes is not affected.

#43 webpack-dev-server users' source code may be stolen when they access a malicious web site — Dev-only but genuinely reachable. react-scripts@5.0.1 (devDependency, package.json:83) pulls webpack-dev-server@4.15.2 (package-lock.json:21657, dev:true; declared at :17884), which is in range <=5.2.0. The dev server is actually run: package.json scripts.start runs `craco start` and README.md:26 documents `npm start` on localhost:3000. CVE-2025-30359 targets exactly that scenario - a developer running the dev server who visits a malicious site, leaking private source. Reachability is established, so not_used is wrong, and source-code exfiltration from a private commercial repo is not an impact I can call acceptable on the maintainers' behalf. Recommended: Bump webpack-dev-server to 5.2.1+. Breaking for us: react-scripts@5.0.1 pins ^4.6.0, so this needs an npm `overrides` entry, and v5 has breaking dev-server config changes. react-scripts 5.0.1 is unmaintained, so the durable fix is migrating off CRA/craco. 
https://github.com/teqplay/terminal-planner/security/dependabot/43
#42 Babel has inefficient RegExp complexity in generated code with .replace when transpiling named capturing groups — The alert is accurate and points at a nested copy that ships to production. Top-level @babel/runtime is 7.27.1 (package-lock.json:2130, not vulnerable), but react-event-listener@0.5.10 pins its own @babel/runtime@7.0.0-beta.42 (package-lock.json:17552-17553) with no dev flag, so runtime scope - and 7.0.0-beta.42 sorts below 7.26.10. That copy is shipped: react-scrollbar-size is a direct runtime dependency (package.json:47) that requires react-event-listener ^0.5.1 (package-lock.json:17965), and it is rendered in src/components/app/App.js:264. Exploitation additionally requires the intermediate package to use the wrapRegExp helper (named capturing groups) and apply .replace to attacker-controlled input. I could not verify react-event-listener's internals because node_modules is absent, so per fail-closed this is not dismissable. Recommended: Bumping the top-level will not clear this - it is already 7.27.1. Add an npm `overrides` forcing @babel/runtime >=7.26.10 for react-event-listener (low breaking risk; the helper API is stable), or drop react-scrollbar-size, which has been unmaintained since 2018 (requires a code change in App.js). 
https://github.com/teqplay/terminal-planner/security/dependabot/42
#40 Sentry SDK Prototype Pollution gadget in JavaScript SDKs — Direct runtime dependency, live in production. @sentry/browser is pinned at 5.15.5 (package.json:7, package-lock.json:3846), well below the 7.119.1 first-patched version, and it is not dev-scoped. It is initialized for every non-localhost environment at src/js/sentry.js:17 and also imported at src/pages/login/Login.js:3. The prototype-pollution gadget lives in the SDK's event normalization, and we feed it arbitrary attacker-influenceable data: src/js/sentry.js:52 and :67 call scope.setExtra over caller-supplied objects, and src/js/sentry.js:89 passes a raw API error response through. Reachable in shipped code, so no dismissal reason applies. Recommended: Bump @sentry/browser to 7.119.1. Breaking for us: that is a two-major jump (5.x to 7.x) with changed init options and integration APIs; src/js/sentry.js and src/pages/login/Login.js need review, and @sentry/cli@1.53.0 plus scripts/sentryRelease.js should be updated alongside it. Note the gadget only escalates an existing prototype-pollution primitive, so this is upgrade-soon rather than emergency. 
https://github.com/teqplay/terminal-planner/security/dependabot/40
#26 PostCSS: incomplete fix of GHSA-6g55-p6wh-862q — attacker-controlled sourceMappingURL reads arbitrary .map files when `from` is unset — Unlike alert 38, this range (<=8.5.22) captures BOTH postcss copies: top-level 8.5.3 (package-lock.json:15260, dev:true) and the nested 7.0.39 under resolve-url-loader (package-lock.json:18702). The top-level copy is the one react-scripts drives through postcss-loader across the whole CSS pipeline, including CSS imported from node_modules (leaflet, fontawesome, react-toastify, rc-calendar), so the blast radius is wider than the Sass-only path. Whether the bug triggers depends on postcss-loader leaving `from` unset, which I could not verify - node_modules is absent and I could not install it. The impact if it does fire is an arbitrary local .map file read during a build that runs in CI holding AWS, Sentry and npm credentials (.github/workflows/main.yml:20-24). Scope is established but reachability is not, so this fails closed. Recommended: Bump top-level postcss to 8.5.23 - non-breaking, it is a patch within 8.x and dev-only. The nested resolve-url-loader copy cannot reach 8.5.23 (it expects the postcss 7 API), so an override there would be breaking; leave it, since alert 38's analysis shows that copy only ever sees first-party SCSS. 
https://github.com/teqplay/terminal-planner/security/dependabot/26
#3 webpack-dev-server vulnerable to cross-site request forgery via internal developer endpoints — Same dev-only chain and same reachability as alert 4 - webpack-dev-server@4.15.2 (package-lock.json:21657, dev:true) via react-scripts (package-lock.json:17884), actually run via `npm start` (README.md:26) - but the impact class is different and I will not dismiss it. CVE-2026-14620 is CSRF against the dev server's internal developer endpoints, driven by any site a developer visits while the server is running. Unlike the pure DoS in alert 4, the consequences depend on what those internal endpoints expose, and craco.config.js sets no devServer overrides (it only patches source-map-loader), so we run CRA 5 defaults that I could not inspect with node_modules absent. Reachable with unquantified impact, so this fails closed rather than being accepted as tolerable. Recommended: Bump webpack-dev-server to 5.2.6 via an npm `overrides` entry. Breaking for us: react-scripts@5.0.1 pins ^4.6.0 and v5 changed dev-server config; same underlying constraint as alert 43, so fix both together. Interim mitigation: set HOST=127.0.0.1 so the dev server is not bound to all interfaces.
