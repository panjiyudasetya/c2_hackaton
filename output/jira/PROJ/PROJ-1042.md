What triage found
#53 Vite Vulnerable to Path Traversal in Optimized Deps `.map` Handling — vite is a direct devDependency pinned at 6.2.0 (package.json devDependencies; pnpm-lock.yaml:5372), squarely inside the vulnerable range <= 6.4.1. The path traversal is in the dev server's optimized-deps `.map` handling, and the dev server is exactly what `pnpm start` runs (package.json scripts.start = `vite`) on localhost:3000 with `open: true` (vite.config.ts:8-11). The vulnerable component therefore runs routinely on developer machines; a malicious page visited while the dev server is up can issue drive-by requests to it. I cannot establish non-reachability with evidence, so per fail-closed this is not dismissable. Note: `gh` CLI invocations were blocked by the permission layer in this session, so I could not enumerate open PRs; however `git branch -a` shows no dependabot/bump/renovate branch, so fix_started is unsupported. Recommended: Bump vite to 6.4.2 (first patched). This is a minor bump within v6 and also closes alert #28 (GHSA-93m4-6634-74q7, patched in 6.4.1), so one bump resolves both. Not a breaking change for this project: vite.config.ts uses only base/plugins/server/build/test options, all stable across 6.2→6.4. 
https://github.com/teqplay/vesselcompliance/security/dependabot/53
#28 vite allows server.fs.deny bypass via backslash on Windows — vite 6.2.0 (package.json devDependencies; pnpm-lock.yaml:5372) falls in the vulnerable range >= 6.0.0, <= 6.4.0. The server.fs.deny bypass is exploitable only on Windows, and this machine is darwin — but that is one developer's machine, not the team's. package.json declares no `os` field and nothing in the repo constrains contributors to macOS/Linux, so I cannot establish with evidence that no developer runs the dev server on Windows. Per fail-closed, an unverifiable OS precondition is not grounds for dismissal, particularly since `pnpm start` runs the vulnerable dev server directly (package.json scripts.start) and the fix is trivial. Separately: `gh` was blocked by the permission layer this session so I could not list open PRs, but `git branch -a` shows no dependabot/bump/renovate branch, so fix_started is not supportable. Recommended: Bump vite to 6.4.1 or later; take 6.4.2, which also closes alert #53 (GHSA-4w7w-66w2-5vf9). 6.2.0 → 6.4.2 is a minor bump within v6 and is not breaking for this project — vite.config.ts uses only base/plugins/server/build/test, all stable across 6.2→6.4. 
https://github.com/teqplay/vesselcompliance/security/dependabot/28
#17 Babel has inefficient RegExp complexity in generated code with .replace when transpiling named capturing groups — NOT dismissable - fails closed. @babel/runtime@7.26.7 (pnpm-lock.yaml:188) is below the 7.26.10 patch line and is a genuine runtime-scope transitive dependency that ships to production: it is pulled in by react-beautiful-dnd (pnpm-lock.yaml:4813), react-redux (:4871), react-select (:4895), react-transition-group (:4922), redux (:4944) and @emotion/react (:2831), and react-select plus react-beautiful-dnd are production dependencies (package.json:20, :14) imported across 42 files in src/. Our own code cannot trigger the flaw - src/ contains no @babel/runtime import and is compiled by SWC/esbuild, not Babel - but the advisory concerns the wrapRegExp helper emitted inside those third-party packages' prebuilt dist files, and node_modules is not installed in this checkout (ls -d node_modules/.pnpm returned NO_NODE_MODULES), so I cannot grep the intermediate packages for wrapRegExp usage. Reachability of the vulnerable helper is therefore unestablished, and per fail-closed policy that means no dismissal. Recommended: Bump @babel/runtime to 7.26.10 (or later 7.26.x). It is transitive, so pin via a pnpm override or `pnpm update @babel/runtime` - a patch-level bump, not a breaking change for us. To dismiss instead, install node_modules and grep the shipped dependency dist for wrapRegExp / $<name> replace usage. 
https://github.com/teqplay/vesselcompliance/security/dependabot/17
#16 launch-editor: NTLMv2 hash disclosure via UNC path handling on Windows — NOT dismissable - fails closed. vite 6.2.0 (package.json:82) is well below the 6.4.3 patch line. launch-editor does not appear as its own node in the lockfile (Grep 'launch-editor' over pnpm-lock.yaml returned no matches) and vite's own resolved dependency list is only esbuild, postcss and rollup (pnpm-lock.yaml:5372-5380), which would suggest the package is absent - but the advisory is filed against vite itself with a vite patch version, implying the affected handling is inlined into vite's bundled dist. I cannot confirm either way: node_modules is not installed (NO_NODE_MODULES) so vite's dist cannot be grepped for an open-in-editor endpoint, and advisory text was unreachable (gh api and WebSearch both blocked in this sandbox). The dev-only, localhost-bound argument does not rescue this one either: an editor-launch endpoint is triggerable by a page loaded in the developer's own browser, and the attack leaks an NTLMv2 hash from a Windows developer machine rather than requiring LAN exposure. Whether any teammate develops on Windows is also not establishable from this repo. Recommended: Bump vite to 6.4.3 (dev dependency). 6.2.0 -> 6.4.3 stays within vite 6, so it is not a breaking change for us; this single bump also closes alerts 13, 8, 5, 4, 21 and 22. 
https://github.com/teqplay/vesselcompliance/security/dependabot/16
#13 Vite Vulnerable to Path Traversal in Optimized Deps `.map` Handling — NOT dismissable - fails closed. vite 6.2.0 (package.json:82) is inside the <= 6.4.1 range. It is a dev-only dependency, but unlike the three server.fs.deny bypasses this flaw is in the dev server's handling of optimized-dep .map requests - a normal, browser-issuable URL path, needing no malformed request-target or non-normalizing client. A page a developer visits while running `pnpm start` could therefore reach it on localhost, and vite 6.2.0 predates the later dev-server origin/CORS hardening, so a cross-origin read cannot be ruled out. This advisory postdates my knowledge cutoff and I could not retrieve its text (gh api and WebSearch both blocked here), so I cannot confirm the preconditions or that a localhost-only bind is sufficient mitigation. Note the project root contains a .env file (ls -a), which is the kind of asset a dev-server path traversal would expose. Recommended: Bump vite to 6.4.3 (covers this alert's 6.4.2 floor and every other vite alert). Within vite 6, so not a breaking change for us. 
https://github.com/teqplay/vesselcompliance/security/dependabot/13
