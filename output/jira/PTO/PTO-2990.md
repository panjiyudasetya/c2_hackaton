# [PTO-2990] No stream consumption for more than 15mins on POCCA environment

## Description

Our investigation currently points to two primary suspects for the observed lack of stream consumption:
Infrastructure-related instability: Pod restarts are primarily associated with the git-sync-dags and git-sync-plugins sidecars rather than the Airflow application containers. This indicates a potential infrastructure or deployment issue rather than Airflow containers restarting due to resource exhaustion.
Airflow streaming/listening behavior: RabbitMQ ConnectionResetError events were observed on the worker connection, indicating a potential connection, heartbeat, or network issue while Airflow is listening to the stream.
Evidence
kubectl describe pod airflow-pocca-triggerer-0 airflow-pocca-scheduler-554776889f-cjbzn airflow-pocca-worker-0 -n data-engineering | grep -E "^Name:|^  [a-z][a-z-]+:|Restart Count:|Exit Code:|Reason:"
Airflow application containers show 0 restarts:
triggerer: 0
scheduler: 0
worker: 0
Most pod restarts originate from Git Sync sidecars:
git-sync-dags: 11 to 17 restarts
git-sync-plugins: 12 to 14 restarts
RabbitMQ connection resets were observed between the Airflow worker (172.31.16.106) and RabbitMQ.
Initial Assessment

The current evidence does not indicate OOM or Airflow container restarts as the cause of the stream consumption issue. The investigation should therefore focus on:
Infrastructure stability, particularly the Git Sync sidecars and their restart events.
Airflow to RabbitMQ stream connectivity, including connection resets, heartbeat handling, and network interruptions.
The next step is to determine whether these infrastructure and RabbitMQ connection events correlate with the periods of no stream consumption.

* {{git-sync-dags}} failed on *2026-08-11*: {{RPC failed; curl 16 Error in the HTTP2 framing layer}}

*This theory was ruled out.* Three reasons:

# The git-sync crashes started in *early August*, while the stream DAG failures occurred on *2026-09-03*, a month gap with no temporal correlation.
# The Airflow *worker container itself had* {{Restart Count: 0}} on all pods. Git-sync is a sidecar that only syncs DAG code, it does not affect running tasks, open connections, or the Celery worker process.
# The RabbitMQ broker logs show *no corresponding events* at the git-sync crash timestamps. The broker logs are continuous with no anomalies in August.

Git-sync failures are a separate deployment concern (new code won't reach the worker until fixed) and are not a cause of the September 3 connection resets.

*Key patterns from the broker logs:*

* *71 of 91 heartbeat kills* happened at exactly {{duration: '3M, 0s'}}. This is not a coincidence, it is the precise fingerprint of the failure mechanism: ~30s consuming messages + broker waits {{2 × 60s = 120s}} of heartbeat silence before killing = ~3 minutes total connection lifetime.
* *18 kills* at {{duration: ‘30M, 0s'}}. It is long-idle connections in the connection pool that the broker also eventually killed due to sustained heartbeat silence.
* The *channel crash dumps* (Erlang {{** Generic server terminating}}) show {{{1500}} as the prefetch count and {{pending_ack}} entries for the {{VesselVoyage-PTO-pocca-barge}} queue, confirming 1,500 unacknowledged messages were in-flight when the connection was killed.
* The *11:xx window* shows consistently high connection churn (5–12 {{client unexpectedly closed}} events per minute for the entire hour), indicating elevated queue activity and more concurrent instances finishing consumption simultaneously, amplifying the lock contention problem.

*The exact failure sequence every time:*

{noformat}Airflow worker: channel.consume() loop runs     ← pika event loop active, heartbeats sent
                loop exits (batch complete)     ← pika event loop STOPS
                _filter_data()                  ← no heartbeats sent
                _persist_update_messages()      ← DB UPSERT blocks (lock contention)
                ...120+ seconds of DB work...
RabbitMQ broker: "missed heartbeats, timeout: 60s" → TCP RESET sent to worker
Airflow worker: basic_ack()  → StreamLostError
                basic_nack() → ChannelWrongStateError  ← masks real error in logs
Airflow: task marked FAILED
{noformat}

The lock contention is caused by *3 concurrent DAG instances* each holding up to 1,500 unacknowledged messages and all trying to upsert into {{staging_sof}} simultaneously. Instance B and C block on Instance A's transaction lock for the duration of A's upsert, extending the heartbeat silence window well beyond the 120s broker tolerance.

h3. *3. Conclusion and Fixes*

*Root cause:* Pika's {{BlockingConnection}} stops sending heartbeats during DB persistence. With the broker's default 60s heartbeat, any persistence run blocked by lock contention beyond 120s results in a broker-side TCP reset. Three concurrent DAG instances with 1,500 messages each is enough to reliably trigger this under moderate load.

*Secondary bug:* {{DeferredAckHandler.rollback()}} called {{basic_nack()}} on an already-dead channel, raising {{ChannelWrongStateError}} which replaced the real {{StreamLostError}} in Airflow task logs — making the root cause invisible until now.
