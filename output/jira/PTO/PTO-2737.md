# [PTO-2737] Priority Port Processing — Reduce Batch Wait Time for Top-Priority UNLOCODEs

**URL:** https://teqplaybv.atlassian.net/browse/PTO-2737  
**Type:** Story | **Status:** To Do | **Priority:** Medium

**Board:** PTO board  

## Description

Currently, all ports are processed using *FIFO ordering* ({{ORDER BY updated_at ASC}} / {{created_at ASC}}) across the SOF and Operational Events streaming pipelines. This FIFO discipline is intentional — it ensures that no port is starved regardless of message arrival patterns, and it underpins the anti-starvation guarantees already present in the system:

* *SOF stream:* {{ORDER BY updated_at ASC}} ensures oldest pending records are always promoted first, preventing queue pile-up at non-priority ports.
* *Vessel operational queue:* {{ORDER BY created_at ASC}} with {{SELECT FOR UPDATE SKIP LOCKED}} ensures fair, concurrent-safe consumption.
* *Recovery stream:* A two-level anti-starvation ordering — {{ORDER BY recovery_attempts ASC, deferred_at ASC}} — ensures that freshly deferred records don't starve chronically stuck ones, and chronically stuck ones don't block fresh ones from recovering.

However, this flat FIFO model means records for high-value, top-priority ports (e.g. {{NLRTM}}, {{BEANR}}) sit in the queue alongside all other ports and are processed purely in arrival order. The result is unpredictable and often excessive waiting time for priority port data to flow through ODS → Fact layers, directly impacting data freshness SLAs for those customers.

*Goal:* Introduce a priority tier on top of the existing FIFO and anti-starvation ordering, so that priority port records are consistently picked up at the front of every processing batch — *without removing starvation protection for non-priority ports*. Non-priority records must still make forward progress under the existing FIFO guarantees; priority ordering only controls which records are picked first within a batch, not whether non-priority records are processed.

*Affected DAGs:*

* {{ods_sof__stream}}
* {{ods_sof__recovery_stream}}
* {{fact_sof__stream}}
* {{fact_operational_events}}
