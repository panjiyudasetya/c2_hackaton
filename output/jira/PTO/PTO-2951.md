h3. *FIX 1*Zero-duration event at a month boundary

Force the edge case: a visit whose {{start_timestamp}} and {{end_timestamp}} are identical and land exactly at midnight on the 1st. Pick any real {{berth_visit_id}} from the test port and repoint it:

{code:sql}UPDATE fact_berth_visit
SET start_timestamp = '2025-03-01 00:00:00',
    end_timestamp   = '2025-03-01 00:00:00'
WHERE berth_visit_id = '<pick one from USCRP>';{code}

Rerefresh {{enriched_berth_visit_monthly_stay}} and {{gold.kpi_berth_stay_duration_monthly}} for March 2025, then:

{code:sql}SELECT berth_visit_id, calendar_month, has_stay_data, berth_stay_hours
FROM silver.enriched_berth_visit_monthly_stay
WHERE berth_visit_id = '<same id>';{code}

*Expect:*

Exactly one row, {{calendar_month = 2025-03-01}}, {{has_stay_data = false}}, {{berth_stay_hours = 0}}. Before the fix this query returned *zero rows* — the visit vanished entirely.

* Boundary visit produces exactly one row and is counted in {{all_berth_visit_count}}

h3. *FIX 2*Ongoing visit with no mooring data

Find a visit still at berth (no {{end_timestamp}}) that also has no mooring timestamps — or force one:

{code:sql}UPDATE fact_berth_visit
SET end_timestamp = null, start_mooring_timestamp = null, end_unmooring_timestamp = null
WHERE berth_visit_id = '<pick one>';{code}

{code:sql}SELECT berth_visit_id, calendar_month, has_mooring_data, mooring_hours
FROM silver.enriched_berth_visit_monthly_mooring
WHERE berth_visit_id = '<same id>';{code}

*Expect:*

One row, anchored to the visit's {{start_timestamp}} month, {{has_mooring_data = false}}, {{mooring_hours = 0}}. Before the fix: no row at all — it matched neither the "has mooring data" nor the "missing but completed" branch.

* Ongoing + no-mooring-data visit produces one zero-contribution row

h3. *FIX 3*Unresolved ship never breaks the load

{code:sql}SELECT ship_type, count(*)
FROM gold.kpi_portcall_duration_monthly
GROUP BY ship_type
ORDER BY 2 DESC;{code}

*Expect:*

Every row has a non-null {{ship_type}}. If an {{'UNKNOWN'}} bucket appears, it should be a small minority — a large one means {{ship_id}} resolution against {{dim_ship}} is broken, not just an occasional unmatched vessel.

Repeat the same shape of check on the other three affected tables:

{noformat}gold.kpi_berth_stay_duration_monthly
gold.kpi_berth_occupancy_monthly
gold.kpi_portcall_performance_monthly{noformat}

* No null {{ship_type}} anywhere; {{'UNKNOWN'}} bucket (if any) is a small minority

h3. *FIX 4*Exchange-hours denominator matches the numerator's grain

{code:sql}SELECT terminal_id, calendar_month,
       total_vessel_exchange_hours, all_vessel_exchange_count,
       total_vessel_exchange_hours / NULLIF(all_vessel_exchange_count, 0) AS recomputed,
       all_avg_vessel_exchange_hours
FROM gold.kpi_terminal_occupancy_monthly
WHERE all_vessel_exchange_count > 0
ORDER BY calendar_month DESC
LIMIT 20;{code}

*Expect:*

{{recomputed}} equals {{all_avg_vessel_exchange_hours}} for every row (float rounding aside). Run the mirror check against {{gold.kpi_overall_port_performance_monthly}}. Before the fix, a multi-month empty-quay gap would deflate this average in every month except the departure month.

* Recomputed ratio matches stored {{all_avg_vessel_exchange_hours}} on both Gold tables

h3. *FIX 5*Pairs with no valid operational timestamps still count

{code:sql}SELECT berth_id, calendar_month, exchange_count, all_vessel_exchange_count, vessel_exchange_count
FROM silver.enriched_berth_exchange_monthly
WHERE all_vessel_exchange_count > vessel_exchange_count
ORDER BY calendar_month DESC
LIMIT 20;{code}

*Expect:*

Rows exist where {{all_vessel_exchange_count > vessel_exchange_count}} — proof that invalid-timestamp pairs are being picked up by the "all" denominator instead of quietly falling through a null {{exchange_calendar_month}}.

* At least one berth/month shows {{all_vessel_exchange_count > vessel_exchange_count}}
