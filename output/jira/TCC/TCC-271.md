## Description

Over the weekend of 12-13 July 2025 VesselVoyage queue got stuck, this resulted in a couple of tasks being created to be picked up with high-prio, given the rate of instabilities triggered 2 prio 1 calls in only 48 hours.

Meeting notes:


{noformat}Assumptions on cause for now (real in-depth analysis will be Wednesday):
Movement of in-memory state to database has made the database use a lot more heavy, and enhanced locking mechanism, might have introduced some side-effects. We will move back to the in-memory state (and keep the enhanced locking).
Darius / Joostd will roll-back today where we scaled up things Saturday Morning, which seemed to have no effect:
- Vesselvoyage
   - reduce mem back to original
   - Reduce cpu back to original
- Remove newly added node to the cluster
- Vesselvoyage mongo Database
  - reduce CPU to 0.5 (The memory increase has allowed to cache responses / indexes, speeding-up the db, so we keep that doubling for now)
Darius / Joostd Actions for now:
- Throughput increase by introducing in-memory state again
- Try-catch everywhere fix blocking threads
- Health actuator - NATS client restarten when not consuming
- Document the configuration options in thread distribution
Vesselvoyage team Actions for the Longer term:
- Why still processing all these ais events?
- (after switching off v1) Reconsider the resources being used being correctly sized{noformat}
