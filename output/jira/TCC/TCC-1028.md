# [TCC-1028] Ensure 404 responses work correctly

**URL:** https://teqplaybv.atlassian.net/browse/TCC-1028  
**Type:** Bug | **Status:** To Do | **Priority:** Medium  
**Reporter:** Michel Wilson | **Assignee:** Michel Wilson  
**Created:** 2026-06-18 | **Updated:** 2026-07-01  
**Board:** TCC board  
**Labels:** NeedsRefinement  

## Description

Currently, when users access non-existent endpoints in applications using the skeleton-plugins security configuration, they receive a *401 Unauthorized* error instead of the more appropriate *404 Not Found* error. This creates poor user experience because:

# Users cannot distinguish between "this endpoint doesn't exist" vs "you need authentication to access this endpoint"
# API discovery becomes unnecessarily difficult - users shouldn't need authentication just to determine if an endpoint exists
# This violates REST best practices where 404 should indicate resource/endpoint doesn't exist

h3. Current Behavior

* {{/actuator/prometheus}} → 401 (should work if whitelisted)
* {{/api/users}} → 401 (correct - requires auth)
* {{/does-not-exist}} → 401 (incorrect - should be 404)

h3. Desired Behavior

* {{/actuator/prometheus}} → 200 (if whitelisted)
* {{/api/users}} → 401 (requires auth, endpoint exists)
* {{/does-not-exist}} → 404 (endpoint doesn't exist)

h2. Root Cause

The {{ApiWebSecurityConfiguration}} in skeleton-plugins uses Spring Security's default {{Http401UnauthorizedEntryPoint}}, which returns 401 for all unauthenticated requests, regardless of whether the endpoint actually exists.

h2. Solution Overview

Replace the default authentication entry point with a "smart" entry point that:

# Checks if a Spring MVC handler (controller method) exists for the requested URL using {{RequestMappingHandlerMapping}}
# If NO handler exists → return *404 Not Found*
# If handler EXISTS but user is not authenticated → return *401 Unauthorized*

This maintains security while improving UX - authenticated endpoints still require auth, but non-existent paths correctly return 404.
