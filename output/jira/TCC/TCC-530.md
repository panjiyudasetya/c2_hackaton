# [TCC-530] VesselVoyage nats consumer can get stuck indefinite when calling drain

## Description

h2. Description

on VesselVoyage DEV the AIS consumer suddenly stopped. However, looking at the logs it seems that it was related to it fully stopping any AIS consuming for almost 5 minutes and the refresh consumer mechanism kicked in.

{noformat}2025-11-11 07:20:57,027 [34mINFO [0;39m [[36mscheduling-2[0;39m] [33mn.t.v.s.q.AisStreamingMessageHandler[0;39m: Last AIS message received at 2025-11-11T07:15:52Z (age = 304 seconds, max = 300)
2025-11-11 07:20:57,027 [31mWARN [0;39m [[36mscheduling-2[0;39m] [33mn.t.v.s.q.AisStreamingMessageHandler[0;39m: No AIS message received in the allowed idle time. Refreshing ais-stream consumer.
2025-11-11 07:20:57,028 [31mWARN [0;39m [[36mscheduling-2[0;39m] [33mn.t.v.s.q.AisStreamingMessageHandler[0;39m: Refreshing ais-stream consumer and clearing lanes...{noformat}

This didn’t work as it executes the following code:


{noformat}    private fun refreshConsumer() {
        try {
            log.warn { "Refreshing ais-stream consumer and clearing lanes..." }

            // Step 1: Stop the consumer from receiving new messages
            consumerStream?.drain()
            log.info { "Consumer drained, no new messages will be received" }

            // Step 2: Clear all lanes
            clearLanes()

            // Step 3: Restart the consumer subscription
            consumerStream?.consume { wrapper, message ->
                handleConsumerMessage(wrapper, message)
            }

            log.info { "Successfully refreshed ais-stream consumer and cleared lanes" }
        } catch (e: Exception) {
            log.error(e) { "Failed to refresh ais-stream consumer" }
        }
    }{noformat}

It would get stuck at step 1 because draining the consumer has no timeout, meaning it will wait forever (as stated in the NATS library):

{code:java}    /**
     * Drain tells the consumer to process in flight, or cached messages, but stop receiving new ones. The library will
     * flush the unsubscribe call(s) insuring that any publish calls made by this client are included. When all messages
     * are processed the consumer effectively becomes unsubscribed.
     * 
     * A future is used to allow this call to be treated as synchronous or asynchronous as
     * needed by the application.
     * 
     * @param timeout The time to wait for the drain to succeed, pass 0 to wait
     *                    forever. Drain involves moving messages to and from the server
     *                    so a very short timeout is not recommended.
     * @return A future that can be used to check if the drain has completed
     * @throws InterruptedException if the thread is interrupted
     */
    public CompletableFuture<Boolean> drain(Duration timeout) throws InterruptedException;{code}

Because draining will wait until all in-flight messages are processed, not having a timeout will result in the VesselVoyage stopping processing AIS in this case.

Instead we should most likely have a timeout, or just close the connection directly because the refreshConsumer method is only called after 5 minutes of not receiving any messages. 

h2. Definition of Done

* Timeout is reproduced and made fix doesn’t brick the connection.
* Connection is properly refresh and no monitoring message is send in slack when the connection bricks
