## Comments

### Darius Wattimena — 2026-08-06

*Root cause found for the duplicate key error on recalculation* (E11000 on {{encountersV2}} during repair story / full story recreate):

Normalized child documents have deterministic IDs ({{"{entryId}:{startEventId}"}} for encounters), so a recalculation regenerates exactly the same IDs. The diff-based save ({{buildDiffWriteModels}}) wrote _new_ documents as *inserts*, so any leftover document — e.g. an encounter orphaned by an earlier partial write, which cleanup misses because it isn't referenced in the parent {{NormalizedESoF}}'s ID lists — fails the entire entry's bulk write with a duplicate key error. The recalculation then continues with a half-written story since the persist error is swallowed.

*Fix:* write new documents as upserting replaces instead of inserts. Because the IDs are deterministic, a stale leftover is simply overwritten with the freshly calculated version — recalculations now self-heal corrupted state instead of getting stuck. This covers all five normalized child collections (encounters, slow moving periods, STS transfers, area activities, stops) since they share the same diff utility.

PR: https://github.com/teqplay/vesselvoyage-backend/pull/845

Note: an orphan that the new story does _not_ regenerate still lingers in the DB (harmless for writes, but can surface via entryId-based queries). If needed, a follow-up could add an entryId-based sweep to {{recreateFullShipStory}} as belt-and-braces cleanup.
