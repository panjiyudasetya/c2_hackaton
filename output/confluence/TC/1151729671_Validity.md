## Architecture Overview

**Validity testing** is a data quality validation layer that enforces constraint-based rules on fact tables in the DATA\_MART schema. It operates independently of source data comparison, focusing on intrinsic data integrity.

## Validity Score Algorithm

### Score Calculation Formula:

wide760Validity Score = (Valid Rows / Total Rows) × 100

**Time Complexity**: O(1) - constant time calculation after validation

**Space Complexity**: O(k) - where k is the number of invalid rows stored

### Implementation:

**File**: `teqplay/services/quality/validity/base_validity.py`

wide760score = (
round((valid\_rows / total\_rows \* 100), 2)
if total\_rows > 0
else 100.0 # Default to 100% if no rows to validate
)
status = "PASSED" if valid\_rows == total\_rows else "FAILED"

### Aggregated Score Calculation:

**File**: `teqplay/tasks/quality/validity/utils.py`

wide760 if not validity\_checks:
return 100.0
total\_valid\_rows = sum(
result.get('valid\_rows', 0)
for result in validity\_checks.values()
)
total\_rows\_checked = sum(
result.get('rows\_count', 0)
for result in validity\_checks.values()
)
return (
round((total\_valid\_rows / total\_rows\_checked \* 100), 2)
if total\_rows\_checked > 0
else 100.0
)

### Example Calculation:

**Scenario**: Port Visit with 1,000 records

| Check | Valid Rows | Total Rows | Individual Score |
| --- | --- | --- | --- |
| `turn_around_time_duration_non_null` | 995 | 1,000 | 99.50% |
| `total_moored_duration_non_negative` | 998 | 1,000 | 99.80% |
| `start_timestamp_non_null` | 1,000 | 1,000 | 100.00% |
| `timestamp_logical_order` | 997 | 1,000 | 99.70% |

**Overall Validity Score**:

wide760Total Valid Rows = 995 + 998 + 1,000 + 997 = 3,990
Total Rows Checked = 1,000 + 1,000 + 1,000 + 1,000 = 4,000
Overall Score = (3,990 / 4,000) × 100 = 99.75%

## Validation Rule Types

### 1. **Non-Null Validation**

**Constraint Type**: NOT NULL constraint enforcement

**SQL Equivalent**: `WHERE field IS NOT NULL`

**Time Complexity**: O(n) - single column scan

**Space Complexity**: O(k) - where k is the number of null rows

#### Technical Implementation:

**File**: `teqplay/services/quality/validity/berth_visit_timestamp_validity.py`

wide760 Check that start\_timestamp and end\_timestamp are non-null.
Algorithm:
1. For each timestamp column:
a. Filter rows where column IS NULL
b. Count invalid rows
c. Calculate valid\_count = total\_rows - invalid\_count
d. Collect invalid row identifiers
e. Format result using base class method

### 2. **Non-Negative Validation**

**Constraint Type**: CHECK constraint (value >= 0)

**SQL Equivalent**: `WHERE field >= 0 OR field IS NULL`

**Time Complexity**: O(n) - single column scan

**Space Complexity**: O(k) - where k is the number of negative rows

e. Format result using base class method

**Space Complexity**: O(k) - where k is the number of invalid order rows

### 4. **Sum Validation with Tolerance**

**Constraint Type**: Calculated field consistency with epsilon tolerance **SQL Equivalent**: `WHERE ABS(total - (part1 + part2 + ...)) <= tolerance` **Time Complexity**: O(n) - single row scan with arithmetic operations **Space Complexity**: O(k) - where k is the number of rows exceeding tolerance

#### Technical Implementation:

**File**: `teqplay/services/quality/validity/port_visit_duration_validity.py`

wide760 Check that pilot duration approximately equals sum of activity durations.
Algorithm:
1. Calculate left side: pilot\_duration from timestamps
2. Calculate right side: sum of activity duration fields
3. Calculate absolute difference: |left - right|
4. Filter rows where difference > tolerance
5. Count invalid rows
6. Calculate valid\_count = total\_rows - invalid\_count
7. Collect invalid row identifiers with difference values
8. Format result using base class method

#### Tolerance Configuration:

| Tolerance (hours) | Tolerance (minutes) | Use Case |
| --- | --- | --- |
| 0.01 | ~0.6 minutes (36 seconds) | Strict validation for high-precision data |
| 0.17 | ~10 minutes | **Default** - accounts for timestamp rounding |
| 0.50 | ~30 minutes | Lenient validation for legacy data |

## Performance Considerations

### Optimization Strategies:

1. **Lazy Evaluation**: Use Polars lazy API for large datasets

   df\_lazy = pl.scan\_parquet("fact\_port\_visit.parquet")
   result = df\_lazy.filter(pl.col('duration') < 0).collect()
2. **Batch Processing**: Process data in chunks for very large tables

   BATCH\_SIZE = 100\_000
   for batch in df.iter\_slices(BATCH\_SIZE):
   validate\_batch(batch)
3. **Parallel Execution**: Run domain validations in parallel

   # DAG configuration
   start >> [port\_visit, terminal\_visit, berth\_visit] >> end
4. **Memory Cleanup**: Explicitly cleanup DataFrames after validation

   cleanup\_dataframe(df)
   cleanup\_dataframe(invalid\_df)

### Validity Testing Framework Overview:

| Component | Description | Location |
| --- | --- | --- |

| **Timestamp Validators** | Non-null and logical order checks for timestamp fields | `teqplay/services/quality/validity/*_timestamp_validity.py` |
| **Sum Validators** | Tolerance-based sum validation for calculated fields | `teqplay/services/quality/validity/*_duration_validity.py` |

| **Utility Functions** | Score calculation and result aggregation | `teqplay/tasks/quality/validity/utils.py` |

### Key Technical Concepts:

1. **Validity Score Formula**: `(Valid Rows / Total Rows) × 100`
2. **Four Validation Types**:

   * Non-Null (NOT NULL constraint)
   * Non-Negative (CHECK constraint >= 0)
   * Logical Order (temporal consistency)
   * Sum Validation (calculated field consistency with tolerance)
3. **Three Domains**: Port Visit, Terminal Visit, Berth Visit
4. **78 Total Checks**: 40 non-null + 34 non-negative + 3 logical order + 1 sum validation
5. **Tolerance**: 0.17 hours (~10 minutes) for sum validation
6. **Performance**: O(n) time complexity per check, parallel domain execution

### Comparison: Validity vs. Accuracy:

| Aspect | Validity Testing | Accuracy Testing |
| --- | --- | --- |
| **Purpose** | Enforce constraints | Verify transformations |
| **Data Source** | Single table (Fact) | Two tables (Fact vs. ODS) |
| **Validation Type** | Constraint-based | Comparison-based |
| **SQL Pattern** | `WHERE field IS NULL` | `JOIN ... WHERE fact.field != ods.field` |
| **Performance** | O(n) - single scan | O(n log m) - join operation |
| **Example** | `duration >= 0` | `fact.duration = ods.duration` |
| **Failure Cause** | Data violates constraints | Transformation error |
| **Fix Location** | Source data or ETL logic | Transformation logic |

## Key Takeaways

### For Data Engineers:

1. **Validity testing validates constraints**, not transformations
2. **Use Polars for performance** - O(n) time complexity with lazy evaluation
3. **Explicit memory cleanup** prevents OOM errors on large datasets
4. **Parallel domain execution** optimizes DAG runtime
5. **Tolerance is configurable** for sum validation (default: 0.17 hours)

### For Data Analysts:

1. **Validity score = (Valid Rows / Total Rows) × 100**
2. **100% score = all rows pass validation**
3. **Failed checks indicate constraint violations**, not transformation errors
4. **Invalid rows are tracked** with detailed context for debugging
5. **Overall score aggregates all checks** across all fields

## Glossary

| Term | Definition |
| --- | --- |
| **Validity** | Data conforms to defined formats, types, or allowed domains |
| **Validity Score** | Percentage of rows passing validation (0-100) |
| **Constraint** | Rule that data must satisfy (e.g., NOT NULL, >= 0) |
| **Tolerance** | Acceptable difference for calculated field validation |
| **Invalid Row** | Row that violates one or more validation constraints |
| **Domain** | Logical grouping of related fact tables (e.g., vessel voyage) |
| **Fact Table** | Data mart table containing business metrics |
| **ODS** | Operational Data Store (source data layer) |
| **Polars** | High-performance DataFrame library for Python |
| **Lazy Evaluation** | Deferred execution for query optimization |
