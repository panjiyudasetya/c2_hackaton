## Description

NxtPort v2 (internally named *VesselStayServiceV2*) subsystem is a Portcall+ subsystem to collect the portcall information in the port of Antwerp via NxtPort api (authenticated service).

A portcallPlus scheduled task (type `NXTPORT_V2`) runs every hour (configurable via `nxtPortV2.cycleDuration`) to collect the last portcall information (they call it `stays`) since the last call.

## Agent collection

Formerly, this info was retrieved via the NxtPort api (v1) for free, however, their APIv1 was replaced by APIv2, which still exposes everything for free **except from the agent** (exactly the information we aim to collect).

**This limitation is only applied via the API, though**. Manually the agent’s portcall can be obtain from the Antwerp port website ([link here](https://www.portofantwerpbruges.com/en/shipping/my-port-of-antwerp-bruges#zoek-een-schip)) (see next image):

## MTurk - semi-automated agent collection

An internal component called *MTurk* based on Amazon MTurk and SNS (Simple Notification Service) where we ask MTurk workers to provide from that page the portcall’s agent name of given imo for each new Antwerp portcall.

This component consist of:

1. An **MTurk** Data collection project.

   1. Where instructions are given, as well as a data form is designed.
2. An **SNS** topic.

   1. To forward notifications of new agent provided to the VesselAgent endpoint URL (see point 4).
3. A **logic in PortcallPlus that**, for each new Antwerp Portcall a new MTurk HIT (*Human Intelligence Task*) will be published, using the **MTurk Project LayoutId** together with the **SNS TopicId (its arn)** to get notified.
4. An non-authenticated **PortcallPlus POST endpoint** where to collect the agent name by imo and portcallId (<https://portcallplus.teqplay.nl/v1/mturk/vesselAgent>)

   1. See logic of method [VesselStayServiceV2.convertToPortcall(…)](https://bitbucket.org/teqplay/portcallplus/src/master/src/main/kotlin/nl/teqplay/portcallplus/service/external/nxtport/VesselStayServiceV2.kt#lines-169)

Important note is that AWS Services (both, MTurk and SNS) must use the US-EAST-1 region (N. Virginia).

### HIT publishing flow

Assuming MTurk and MTurkEnabledForNextPort are enabled.

When a new portcall is created in PortcallPlus from NxtPort v2, a new **MTurk HIT** is created with the **MTurk Project Layout Id**. After that, the HIT is updated to get HIT completion notifications via SNS using the **Topic’s arn**, which is linked to the VesselAgent endpoint.  
Then, the HIT is available for MTurk workers in their MTurk dashboard.

We save a `MTurkHITDetails` object (including the HITid, imo and portcallId among others) in the collection `mturk` so to later correlate the future HIT responses and track the entire process.

### HIT assignments processing

Once created, the HIT assignments need to be processed.

They can be done via pull or push. But not both! As side effects might appear.

No big effort has been made to prevent it as via configuration can be prevented and eventually, the push mechanism will disappear (hopefully).

#### Processing MTurk HITs scheduled task (Pull mechanism)

As opposed to the push mechanism, MTurk HITs can be processed in as a Spring scheduled task, defined in `MTurkService.scheduledProcessHits()` method.  
This task will run in a fixed rate period defined in as a Java duration in `mTurk.hitAssignmentsProcessingPeriod`.

This task will run if the MTurkService is enabled (`mTurk.enabled`) and *pullAssigments* is enabled (`mTurk.pullAssignments`).

The method will collect all HITs pending to be processed (not expired, not disappeared from amazon and not an approved answer) and process each one following this draft:

1. fetch the HIT details from MTurk (to get an up-to-date state).

   * If the hit disappeared from Amazon, it’ll be marked as such and early returning it’s processing
2. process all **submitted** HIT assignments

   * This step will **approve or reject** the submitted assignments according to the assessment logic
   * it’ll return the agent based on the submissions (first same agent reaching N results, configurable by `mTurk.minimumSameValidAnswers`)
3. Set portcall agent if it was selected.

   1. It will update the portcall service counter!
4. Expire and delete the HIT if during the processing was marked as such.

   1. Deleting from Amazon is configurable via `mTurk.disposeAfterExpiring`. This option was set for debugging purposes and in a general case, it should be set to true.
5. Persist the HIT in our DB according to the processing result (expired, assignments state, approved answer, etc…).

#### PortcallPlus VesselAgent endpoint (Push method)

Note that this endpoint is for the push method, that is currently disabled (2024-10-15).

This endpoint is called whenever an HIT has been answered my any MTurk worker.

As stated before, the notification is sent via SNS, so, answers come wrapped in a list of answers (`MTurkEventCallBack` model in PC+).

**Each answer** is processed in a loop where we (see diagram below):

1. **Update the saved HIT with their assignments** (fetched from MTurk by the HITid), according to the incoming answer and our own assignment tracking logic.

   * If the amount of HIT assignments is more than the half and all of them are either approved or rejected, the HIT is removed from MTurk (before it’s mandatory to mark it as expired).
2. **Get the answer’s agent** (parsed and de-cluttered)

   * parse the agent name from the answer
   * remove special characters other than alphanumeric ones and uppercase it.
3. **Assess the agent validity** in two cases:

   * If the portcall yet didn’t have an agent set

     + if the agent is an existent registered agent (distinct agents in the `portcall` collection)
   * If the portcall had already an agent set

     + if the answer’s agent matches the portcall’s agent
4. **Check agent validity**

   1. If the **agent** was **valid**

      * **Approve** HIT assignment (hence worker gets paid)
      * **Update portcall** with agent (if not set already) ( this is done twice, as later it’s also updated!)
      * **Mark the HIT as expired** ( why not also deleted?)
   2. if the **agent** was **invalid**

      * Auto-reject mechanism ( it seems to be faulty)

The HIT assessment and related logic based on the assessment result should be reworked because:

* Method names are misleading (they do more of what they state or different logic).
* Some overloaded methods do different things (enough to get confused).
* Operations are often repeated (such as updating twice the portcall’s agent in the same process
* It’s not straight to understand what is doing, hence debugging
* There’s a relevant amount of hidden knowledge (i.e. to delete a HIT it first has to be expired).
* The autoreject mechanism is faulty:

  + It misses one if *leg* (the else block)
  + It is included in the answer’s assessment (it shouldn’t)

## Experimental

At the beginning of 2024-10, C-point site was replaced by [http://www.portofantwerpbruges.com](http://www.portofantwerpbruges.com/).

After some research, the MTurk project in Amazon was updated accordingly. However, the vessel agent obtention is not prevented anymore via google captchas. So, an experimental submodule is set to collect the agent directly from <https://www.portofantwerpbruges.com/api/cpoint/getByNumber?shipType=seaship&number=9235610>, remaining the HITs creation as a fallback in case of not being obtained.

If this proves to be successful, then MTurk might be disabled and relegated. Even, the portcall info collection from Nxtport could be also disabled (replaced by new scheduled task that process portclal information via from the results of [www.portofantwerpbruges.com](https://www.portofantwerpbruges.com/api/cpoint/getByNumber?shipType=seaship&number=9235610).
