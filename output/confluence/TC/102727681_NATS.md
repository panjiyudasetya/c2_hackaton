## Running NATS locally

 docker run --rm --network host -it nats -js

* `--rm` ensures the file system is cleaned up after exiting
* `--network host` ensures the required port (4222) is available on the host machine
* `-it` runs the container interactively
* `nats` is the image (shorthand for `nats:latest`)
* `-js` is a NATS argument that enables JetStream

The image will be pulled if it’s not on your system already, and it will run. Downloading the image shouldn’t take long, as the image is really small.

## Using skeleton-plugins' NATS module

### Setup

The following config values are used:

nats.enabled=false
nats.url=
nats.username=
nats.password=

By default a bean is configured to use these variables (see `NatsClientAutoConfiguration`). Only if `nats.enabled` is set, the bean will be made available, otherwise it will be `null`.

The URL should resemble something like `nats://localhost:4222`, where `localhost` is the server it’s running on and `4222` the default NATS port.

Later in this guide a fault-tolerant NATS server is set up within Kubernetes, the NATS URL for that will be: `nats://nats.brokers.svc.cluster.local:4222`.

The `username` and `password` may be empty for local development. For the NATS running inside Kubernetes you will need appropriate credentials. Later in this guide you can read how to access and modify these.

### Publishing

First, we need to ensure a Stream is available. (<https://docs.nats.io/nats-concepts/jetstream> )

We can do that in code (given we have a `NatsClientBuilder` bean named `natsClientBuilder`):

kotlinval producer = natsClientBuilder.producerStream<Message>(
config = config,
stream = "messages",
subjects = listOf(
"messages.current",
"messages.future",
"messages.public.user",
"messages.private.user"
),
serializer = { objectMapper.writeValueAsString(it).toByteArray() }
)

Here we create a stream, named `messages` where `Message` is the base-type of our message, that will store messages with the listed subjects. The `serializer` can be anything, since NATS just handles byte arrays, but we now use a simple Jackson `ObjectMapper` for JSON.

All `subjects` are listed explicitly now though, it would be easier to use wildcards to ensure we will be less likely to make mistakes by missing newly added subjects along the way.

kotlinval producer = natsClientBuilder.producerStream<Message>(
config = config,
stream = "messages",
subjects = listOf(
"messages.>"
),
serializer = { objectMapper.writeValueAsString(it).toByteArray() }
)

Now all messages starting with `messages.>` will be stored. It’s good practice to start the subject with a unique name, identifying your subject domain. For example `ais.>` for all AIS messages, `ship.>` for ship messages. Something like `event.>` isn’t desired, all messages are “events” already, and this doesn’t explain what the content of the message would be.

For more info about subjects in NATS: <https://docs.nats.io/nats-concepts/subjects>

There are more options to the `producerStream`:

kotlinval producer = natsClientBuilder.producerStream<Message>(
config = config,
stream = "messages",
subjects = listOf(
"messages.>"
),
serializer = { objectMapper.writeValueAsString(it).toByteArray() },
maxAge = Duration.ofDays(3),
replicas = 3,
storeOnDisk = true
)

* `maxAge` is defaulted to `1 hour`

  + this can be higher if required, do note that either the memory or file storage should be able to accomodate the data
* `replicas` is defaulted to `null` and inferred based on the NATS url

  + doesn’t need to be specified, by default the amount of replicas is infered to 1 replica for a `nats://localhost` URL and to 3 replicas otherwise
  + `replicas=3` only works on a clustered NATS setup with 3 replicas, so using a local NATS server only accepts 1 replica
* `storeOnDisk` is defaulted to `false`, meaning it will be stored in memory

  + when restarting a 1 replica / local NATS server:

    - data in memory will (obviously) not survive, should be a non-issue as running locally
    - data on disk will be available still
  + when restarting a 3 replica / clustered NATS server:

    - data in memory will remain available, as long as at least 2 other replicas are still available
    - data on disk will be available still
  + storing on disk should/must only be enabled for data that is critical, like AIS streaming messages

We can now publish a message:

kotlinval ack = producer.publish(
subject = "messages.current",
data = Message("Hello World")
)

The data needs to be a `ByteArray`, you are free to choose what kind of data you’d like to send; JSON, blob data, etc. It is good to stay consistent though, so don’t combine JSON and blob data and distinguish them by the subject. You should use the same kind of data for all messages on the same `stream` even if they have different subjects.

We publish to the `messages.current` subject, do note that this subject is captured by the stream that you just `ensureStream`-ed. This publish is synchronous, so we publish the message and wait for an acknowledgement from the NATS server.

We can also publish messages asynchronously:

kotlinval queue = LinkedBlockingQueue<Message>(...)
val pending = AtomicLong()
val published = AtomicLong()
producer.publishAsync(
queue = queue,
pending = pending,
published = published,
subject = { \_ -> "messages.current" }
)

We will need to use a `LinkedBlockingQueue` for the `publishAsync`. Using asynchronous publishing can be desired if you can batch messages and desire higher throughput. It does come with the extra overhead of using a queue and passing through any pending and published counters. The `publishAsync` will publish the messages for us asynchronously and will attempt retries if required.

Optionally we can also specify a `messageId` for de-duplication:

kotlinproducer.publishAsync(
queue = queue,
pending = pending,
published = published,
subject = { \_ -> "messages.current" },
messageId = { \_ -> "hello-world" }
)

By default, the stream uses a de-duplication (sliding) window of two minutes. So if you send multiple messages with the same `messageId` within that window, only the first message will be stored as the others will be de-duped. It’s desirable to use this if you want to achieve “exactly-once” delivery, otherwise you will achieve “at-least-once” delivery (which might mean data duplication for consumers).

`publishAsync` can be used by calling it in a loop until the `queue` is emptied.

kotlinwhile (queue.isNotEmpty()) {
producer.publishAsync(
queue = queue,
...
)
}

### Consuming

Create a consumer for a specific `stream`:

kotlinval consumer = natsClientBuilder.consumerStream(
config = config,
stream = "messages",
deserializer = { objectMapper.readValue<Message>(it) }
)

This creates a consumer specific to your user and the selected `stream`. The `deserializer` is used to deserialize your message into an object. If you restart the application, NATS will "remember" which messages you've missed in the mean time.

Consume a message:

kotlinconsumer.consume { data, message ->
val subject = message.subject
// TODO: process your data here
message.ack()
}

It’s really really really important to acknowledge your messages! If you don’t you essentially “kill” your app, as you will keep on receiving the same messages.

When consuming a message, you should aim for the following outcomes:

* if the message is not deserializable:

  + if you don’t recognise the `subject` and/or can’t parse the message content, `TERM` the message (`message.term()`), this will stop re-delivery and indicate the message wasn’t successfully processed
  + if you can’t process the message now, but will be able to do so later, then you can use `NAK` (`message.nak()`), the message will be retried later

    - this should be used cautiously, only use this if you are actually able to process the message but are not able currently due to high traffic/load
    - if you are currently working on implementing support for processing this message, then use `TERM` instead! Only use `NAK` to relieve stress of the system and retry later. Don’t use it as a means to retry delivery until your implementation is finished.
  + if you recognise the `subject` (and/or the message content), but want to drop the message as you’re not interested. Feel free to use the `ACK` (`message.ack()`), as a way to silently drop messages.
* now process the message itself

  + don’t surround the processing of this message within a `try-catch` and `ACK` the message anyway (but still be cautious, you might need to acknowledge the message anyhow if it’s about an exception that isn’t recoverable when retrying the delivery)
  + only `ACK` the message if you actually processed the message successfully

This way you can ensure that messages are only redelivered if processing wasn’t successful. For example: when consuming messages, converting them and publishing them somewhere else. On application restart, the consumer’s in-flight messages will be processed still and publishing will be halted. By not using the `ACK`, you can ensure the messages are re-delivered when the restart is complete.

For testing purposes you could configure replaying a stream:

kotlinval consumer = natsClientBuilder.consumerStream(
config = config,
stream = "messages",
deserializer = { objectMapper.readValue<Message>(it) }
)
consumer.consume(
startTime = ZonedDateTime.now().minusHours(2),
replayAtOriginalSpeed = true
) { data, message ->
...
}

Never replay a stream in production, use it only as a means to test or replay certain events.

## Install into cluster

### Create the `brokers` namespace

kubectl create namespace brokers

### Create the users ConfigMap

First we need to create the ConfigMap where are users will reside.

Create a ConfigMap within the `brokers` namespace, and name it `nats-users`. (if the `brokers` namespace doesn't exist, create it)

yamlapiVersion: v1
kind: ConfigMap
metadata:
name: nats-users
namespace: brokers
data:
users.conf: |
accounts: {
}

Within the `accounts` block you can specify accounts and the users, including permissions. (see the relevant sections in these docs)

### Ensure AWS EBS CSI Driver is added

Go to the EKS control panel, and add `aws-ebs-csi-driver` as an Add-on.

Ensure a `gp3-retained` storage class is available. Otherwise, create it with the following content:

yamlapiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
name: gp3-retained
allowVolumeExpansion: true
parameters:
type: gp3
provisioner: ebs.csi.aws.com
reclaimPolicy: Retain
volumeBindingMode: WaitForFirstConsumer

### Install/upgrade NATS

bashhelm upgrade -i -n brokers nats nats/nats -f values.yaml

## Access to the CLI

bashkubectl exec -n brokers -it deployment/nats-box -- /bin/sh -l

## Adding/updating users

In the `brokers` namespace, open the `nats-users` ConfigMap.

The goal for authorization is:

* have an account with multiple users
* accounts provide isolation, so create separate accounts for different "services" (like an `ais` account for AIS related things and a `event` account for event related things, etc.)
* within that account only one user (or a few, but at least a minimal amount) can publish
* all other users can subscribe freely, but aren't allowed to publish anything

> IMPORTANT, usernames must always be unique, even between multiple accounts!

### Adding/update a user within an existing account

Within the `accounts` block, go to the desired account and go to the `users` block.

* username = all lowercase separated by `-`
* password = bcrypt the password, by accessing the CLI and running `nats server passwd`, input the password (at least 22 characters) and copy the resulting bcrypt string
* publish permissions
* if user should only be able to subscribe:  
  (you’ll need to change `ais-stream` to the appropriate protected subject space)

  publish: {
  "allow": ">"
  "deny": "ais-stream.>"
  }
* if user should be able to publish `">"`
* subscribe permissions, always `">"` (meaning all subjects)

js{
user: <username>
password: <password>
permissions: {
publish: <publish-permissions>
subscribe: <subscribe-permissions>
}
}

Make sure the config file is correctly formatted, and go to the `Restarting NATS` section.

### Adding a new account

Go to the `accounts` block and add the following:

* account name = all lowercase separated by `-`

js<account-name>: {
// if JetStream should be available within this account
// otherwise it can be omitted
jetstream: true
users: [
// add users here
]
}

Make sure the config file is correctly formatted, you can now save the ConfigMap.

Every NATS installation has a `reloader` sidecar container, which reloads NATS' config when values are changed. Go to a NATS instance, go to the logs and open those of the `reloader` sidecar. Check that the config was properly reloaded for all instances. Ensuring that all NATS instances have reloaded correctly. It might take a little while before the change is recognised. But stick around to confirm the successful reload! Otherwise NATS will not be able to restart if it has a faulty config.

You’ll see something like the following:

2022/11/04 12:40:19 Starting NATS Server Reloader v0.7.4
2022/11/04 12:40:19 Live, ready to kick pid 8 (live, from 8 spec) based on any of 2 files
2022/11/04 12:42:55 changed config; file="/etc/nats-config/users/users.conf" existing=true total-files=2
2022/11/04 12:42:55 Sending signal 'hangup' to server to reload configuration due to: /etc/nats-config/users/..2022\_11\_04\_12\_42\_55.682106437

The top two lines will always be there, the next lines are indicating the config change was detected and a signal was sent to the server to reload the config. Go to the different instances as well, and check that the config was properly reloaded.

## Resizing JetStream memory and file storage

### Memory

Within the `values.yaml` change the `nats.jetstream.memStorage.size` to the desired value (e.g. `3Gi`) and perform an upgrade.

### File

> IMPORTANT, AWS limits resizes of elastic block storage to once per 6 hours!

Go to the `Persistent Volume Claims` and edit all the NATS-related volume sizes one-by-one.

For every claim, set the `spec.resources.requests.storage` to the desired size (e.g. `5Gi`). After editing, the underlying volumes will be resized automatically.

Go to the AWS console and find the volumes you were resizing. The `Volume state` will transition from `modified` to `optimizing` to `completed`, wait for it to be `completed` (indicated by the green checkmark), this might take a few minutes.

Now you can restart NATS for the changes to take effect, see the section about `Restarting NATS`.

Also verify the `Max Storage` size in the `NATS JetStream` Grafana dashboard is the correct amount after restarting. (If it's not the case, allow for some more time and try the restart again later)

## Restarting NATS

Set up a restart of NATS:

bashkubectl rollout restart statefulset/nats -n brokers

You can track the progress of the rollout by watching the `brokers` namespace for changes: (alternatively you can watch the Pods tab within Lens)

bashkubectl get pods -w -n brokers

If the restart is progressing successfully, you'll see `Running` and `Terminating` statuses

If the restart is failing, you'll see `CrashLoopBackOff` and `Error` statuses. You probably made a mistake in the config, making the startup fail. So, please check the config again and make needed changes. As the pods are still restarting to fix the issue, the ConfigMap change will automatically be picked up.

Once all pods are successfully running, you can exit the command.

You can confirm a succesful rollout by running:

bashkubectl rollout status statefulset/nats -n brokers
