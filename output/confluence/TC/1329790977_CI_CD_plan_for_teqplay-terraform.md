# CI/CD plan for teqplay-terraform

**Space:** TC  
**URL:** https://teqplaybv.atlassian.net/wiki/spaces/TC/pages/1329790977  

## Content

## Principle

PRs produce plans; merges produce deployment requests; deployments create a  
fresh plan and apply exactly what was reviewed/approved.

## Why this shape, and how it fits this repo

A generic hybrid Terragrunt pipeline (PR plans, fresh plan on merge,  
apply-the-exact-approved-plan, per-environment approval) works well here, but  
has to be adapted to what's actually in this repo rather than a generic  
`live/<env>/<region>/<stack>/` layout:

* **Two environments.** `live/test` is being decommissioned; this plan targets  
  `live/dev` and `live/prod` only, each its own AWS account (dev  
  `704630444514`, prod `050356841556`).
* **No region nesting.** The layout is flat:  
  `live/<env>/<component>/terragrunt.hcl` (occasionally one level deeper,  
  e.g. `live/prod/rds/keycloak`, `live/prod/ais-forwarder/ec2`). Region lives  
  in each environment's `env.hcl` (`eu-west-1` for both), except one one-off  
  prod component (`frontends-eu-north-1`) — region is not a dimension the  
  pipeline needs to reason about.
* **OpenTofu, not Terraform.** This repo's `.terraform.lock.hcl` files are  
  generated by `tofu init` and providers resolve from  
  `registry.opentofu.org`. CI must install OpenTofu (`opentofu/setup-opentofu`),  
  not `hashicorp/setup-terraform`, and Terragrunt must be configured to invoke  
  `tofu` instead of its default `terraform` lookup.
* **Real** `dependency` blocks already exist (e.g. `live/*/eks` depends on  
  `live/*/vpc`; the `rds/*` components share a common `rds` include).  
  Affected-component detection should lean on Terragrunt's own dependency  
  graph rather than a hand-rolled dependency map.
* **State locking is already solved.** `root.hcl` sets `use_lockfile = true`  
  on the S3 backend (native S3 locking, no DynamoDB table) — concurrent  
  applies against the same component's state are already prevented by the  
  backend itself. CI-level concurrency groups are about avoiding  
  wasted/queued runs, not preventing state corruption.
* **GitHub OIDC trust already exists in both accounts**  
  (`live/dev/github-oidc`, `live/prod/iam-oidc-providers`, provider  
  `token.actions.githubusercontent.com`) — the missing piece is IAM *roles*  
  for GitHub Actions to assume, not the OIDC provider itself.
* Both dev and prod require a manual approval before apply (via their  
  existing GitHub Environments, just with different reviewer sets). No  
  dedicated security-scanner stage in the first phase (fmt/validate/plan  
  only) — can be added later.
* **Secrets-in-plan risk.** Several Lambda environment variables and the  
  Secrets Manager module's container/version values are plaintext-in-state. A  
  read-only plan role that can call `secretsmanager:GetSecretValue` or read  
  full Lambda environment blocks risks leaking secrets into a PR comment.  
  This must be explicitly denied on the plan role, and the PR comment  
  generator must never dump raw attribute values for those components.

## 2. Affected-component detection

Component identity = its directory path under `live/<env>/`, e.g. `dev/eks`,  
`prod/rds/keycloak`, `prod/frontends-eu-north-1`. No region logic is needed.

`scripts/affected-components.sh` (implemented; verified against Terragrunt  
v1.1.2 and OpenTofu v1.12.2):

1. Changed units come from `terragrunt find --json --filter '[<base>...<head>]'`  
   rather than a hand-rolled `git diff` + path-to-directory mapping. Terragrunt  
   tracks which files each unit reads, so the `modules/` fan-out falls out for  
   free: a change under `modules/iam/` comes back as every `live/*/iam-*` unit  
   that sources it, in every environment. `--filter-allow-destroy` is passed so  
   a range that deletes a unit is describable rather than rejected.
2. The dependency graph comes from a *second*, separate call —  
   `terragrunt find --json --dependencies --dag`. The two must not be combined:  
   with `--filter` in play Terragrunt resolves dependencies inside the  
   temporary git worktree it creates for the range, and the dependency paths  
   come back pointing into that worktree instead of into the repo.
3. The script then computes, from that graph, the transitive **dependents** of  
   the changed units (change `live/dev/vpc` → re-plan `live/dev/eks`, which  
   consumes its outputs) and assigns run levels over the affected subgraph only,  
   so unchanged ancestors do not serialise the apply waves. `--no-dependents`  
   turns the closure off.
4. Output: `--format tree` (default) renders the dependency tree grouped into  
   run levels; `--format json` emits the flat array for a GitHub Actions matrix  
   (`env`, `path`, `name`, `changed`, `reason`, `level`, `dependencies`,  
   `affected_dependencies`); `text` and `dot` are also available.  
   `--github-output` writes `has_changes` / `count` / `envs` / `components` /  
   `<env>_components` / `has_removals` / `removed` to `$GITHUB_OUTPUT`.

Notes for the workflows that consume it:

* Default env scope is `dev,prod`; `live/test` is only reported when named  
  explicitly (`--env test`) or via `--env all`.
* Requires the base commit locally — set `fetch-depth: 0` on  
  `actions/checkout`, since the git filter spawns a worktree at the base ref.
* An empty affected set exits 0 with `[]` and `has_changes=false`, so a  
  docs-only PR does not fail the required status check. Gate downstream jobs  
  on `has_changes == 'true'`; a matrix fed an empty array fails outright.
* Deleted components are reported under `removed`, never as something to run —  
  they need a destroy, which this pipeline does not perform.

## 3. PR workflow (`terraform-pr.yml`)

* Trigger: `pull_request` (opened/synchronize).
* Auth: assume the read-only GitHub Actions role in whichever account(s) the  
  PR's affected components touch (a dev-only PR only needs the dev role; a  
  `modules/` change needs both).
* Steps per affected component: `tofu fmt -check`, `tofu validate`,  
  `terragrunt plan` (no apply, ever).
* PR comment: per-component summary table (add/change/destroy counts) behind  
  a `<details>` block per component, a bold `⚠️ N resources will be destroyed` banner when any plan shows a destroy, and a total. Never paste  
  raw plan diffs for components under `live/*/secrets-manager`,  
  `live/*/lambda`, or any resource showing a full attribute diff involving  
  secret material — summarize counts only for those, link to the full log  
  artifact instead of inlining it.
* Required status check on the PR; no apply credentials ever touch this  
  workflow.

## 4. Deploy workflow (`terraform-deploy.yml`)

* Trigger: `push` to `master`.
* Compute affected components the same way as the PR workflow, but against  
  the previous successfully-deployed commit (store that commit SHA as a  
  workflow output/artifact from the last successful run, or read it back  
  from the target GitHub Environment's deployment history via the API).
* Stage 1 — **dev**: fresh `terragrunt plan` for every affected `live/dev/*`  
  component at the merge commit, save `.tfplan` artifacts, post a deployment  
  summary, then gate on the `dev` GitHub Environment's required reviewer. On  
  approval, `tofu apply <saved-plan>` per component (respecting the  
  Terragrunt dependency order — apply `vpc` before `eks`, etc.).
* Stage 2 — **prod**: only runs for components under `live/prod/*`; same  
  fresh-plan → artifact → `production` Environment approval → apply  
  sequence, independent of dev's outcome (a dev-only change never touches  
  this stage).
* Concurrency group per environment (`deploy-dev`, `deploy-prod`) — this is  
  belt-and-suspenders given `use_lockfile = true` already prevents state  
  corruption; the group just avoids queuing/wasting duplicate runs.
* Deployment manifest artifact (`metadata.json`) per run: commit SHA, PR  
  number, environment, list of affected component paths, OpenTofu version,  
  Terragrunt version, timestamp, workflow run URL.

## 5. Credentials

The OIDC *trust* exists in both accounts already; the *roles* GitHub Actions  
assumes do not. Add them as new Terragrunt components (alongside the existing  
`live/dev/iam-roles` / `live/prod/iam-roles`):

* `github-actions-plan` (per account): trust condition scoped to  
  `repo:teqplay/teqplay-terraform:*` (any branch/PR), permissions = broad read  
  (`ReadOnlyAccess` is a reasonable starting point given how many services  
  this repo touches — EKS, RDS, Lambda, ECR, Route53, IAM, Secrets Manager,  
  SES, ACM, VPC, SNS, KMS, CloudWatch, Backup, security groups) with an  
  explicit deny on `secretsmanager:GetSecretValue`, `ssm:GetParameter*`  
  (decrypt variants), and equivalent secret-value-read actions.
* `github-actions-apply` (per account): trust condition scoped to the GitHub  
  Environment subject claim (`repo:teqplay/teqplay-terraform:environment:dev`  
  / `:environment:production`), permissions = whatever the account's real  
  write footprint requires (broad, since this is the account's actual  
  infra-management role).

Bootstrap order matters: these roles must be applied once using the existing  
named AWS profiles (`dev`/`prod`) before any workflow tries to assume them —  
CI cannot create the credentials it needs to authenticate.

Also confirm and replicate however Terragrunt currently resolves `tofu`  
locally (there is no `terraform_binary` setting committed in `root.hcl`, so  
it is presumably a local PATH/alias choice) — CI needs the equivalent, e.g. a  
`terraform_binary = "tofu"` line in `root.hcl` or a `TERRAGRUNT_TF_PATH`/  
`--tf-path` value set in the workflow, so this doesn't silently diverge  
between local machines and CI.

## 6. Drift detection (`terraform-drift.yml`)

Scheduled (e.g. nightly) `terragrunt run-all plan` across `live/dev` and  
`live/prod` using the same read-only roles as the PR workflow, alerting  
(Slack or a GitHub issue) on non-empty plans. Kept separate from the deploy  
pipeline.

## 7. Implementation phases

**Phase 1 — PR validation only**

* `scripts/affected-components.sh`
* `.github/workflows/terraform-pr.yml`: fmt, validate, plan, PR comment,  
  required status check
* Bootstrap `github-actions-plan` roles in dev + prod (via existing profiles)
* No security-scanner stage yet

**Phase 2 — Deployment pipeline, both environments gated**

* Bootstrap `github-actions-apply` roles in dev + prod
* `.github/workflows/terraform-deploy.yml`: fresh plan → artifact →  
  environment approval (dev, then prod) → apply saved plan
* Concurrency groups per environment
* Deployment manifest artifact + basic audit trail

**Phase 3 — Operational hardening**

* `terraform-drift.yml`
* Retry handling for a failed apply (re-plan from resulting state, don't  
  blindly reapply the stale saved plan)
* Notifications (Slack/Teams) on deploy success/failure and drift
* Revisit adding `tflint`/`checkov`/`trivy` to the PR workflow once the base  
  pipeline is stable

## 9. Alerting

After each Terraform deployment, the CI/CD pipeline should send a Slack notification in terraform-deployment channel containing:

* Environment deployed to
* Deployment status (success/failure)
* Resources changed (created, updated, or destroyed)
* Commit/branch that triggered the deployment
* Link to the CI/CD pipeline for details

This provides the team with immediate visibility into what infrastructure was changed and where.
