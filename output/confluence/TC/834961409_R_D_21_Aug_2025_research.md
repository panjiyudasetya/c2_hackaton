# R&D 21 Aug 2025 research

## Content

SkeletonPlugins is currently a project with 60+ different modules which are used in various project. However, a bunch of them are following the idea of “do it ourself“ instead of reusing any existing functionality found in Spring.

* **models** – Base models used in most of our applications.
* **common** – Shared utilities and base classes.
* **common-network** – Networking utilities and shared network logic.
* **common-internal-api-client** – Client for internal APIs.
* **testing** – Shared testing utilities.
* **actuator** – Spring Boot actuator endpoints for monitoring.
* **atlas-actuator** – Actuator endpoints for Atlas service.

## Proposal

All plugins should only do basic functionality and rely mostly on Spring libraries where needed to avoid our own implementations.

When looking at the big list of modules we see that a bunch of them that can be removed. All client libraries, proxies and application specific auth should be available in the project itself instead. (For example the poma-client).

Next to this we also have a bunch of libraries that haven’t been used for years or are made without the simpleness of what a “skeleton“ library should be.

What this in mind the following list of libraries are proposed:

* **common** – Only containing very basic things that we want to have in all our applications, such as Exception handling.
* **models** – Containing base models used in all applications.
* **location** – basic utility functions to do any calculations where locations are used.
* **auth** – Base necessities needed for authentication, containing both frontend-based and machine-to-machine options, using a lot of the standards already set with Spring OAuth2.
* **auth-keycloak** – Keycloak specific additions needed to make auth work using our own Keycloak set up.
* **validation** – Parameter validation such as Imo number validation.
* **logging** – Configurable incoming and outgoing request logging and logback configuration.

Besides this the following libraries should be replaced with a Spring library instead of our own creation:

* **datasource** – Spring Data
* **rabbitmq** – Spring AMQP

### Example setting up RabbitMQ

Setting up RabbitMQ is very easy with Spring and mainly needs configuration.

spring.rabbitmq.host=localhost
spring.rabbitmq.port=5672
spring.rabbitmq.username=admin
spring.rabbitmq.password=secret

Then we only have to make a bean to get information from a queue:

import org.springframework.amqp.rabbit.annotation.RabbitListener
import org.springframework.stereotype.Component
@Component
class SomeMessageListenerBean {
@RabbitListener(queues = ["someQueue"])
fun processMessage(content: String?) {
// ...
}
}
