## 1. Introduction

Data quality control ensures that data used across analytics, operational systems, and data pipelines is **reliable, consistent, and fit for purpose**. Within our platform, data quality controls are implemented as part of the **data pipeline orchestration layer using Apache Airflow**, executed within a **Kubernetes environment**, and validated against data stored in our **PostgreSQL DWH / Mart**.

Quality checks are embedded directly into the data workflows to detect anomalies early and prevent the propagation of invalid or incomplete data downstream after we are ingesting the data into DWH or Mart.

***Figure 1: Run Quality Control Airflow Task***

We can see here based on the figure 1 that after we are doing some batching ingestions from `Staging` then do some transformations into `ODS` and `FACT` there are `run_quality_control` tasks that will be triggered to proceed our data quality.

The initial focus of the data quality framework is on three foundational dimensions:

* **Completeness**
* **Accuracy / Correctness**
* **Validity**

These checks are executed automatically during pipeline runs and monitored through orchestration logs and metrics.

***Figure 2: Start QC Report Pipeline DAG***

The figure 2 here are the DAG that automatically triggered after batching ingestions. On this DAG there are options to include quality checks on CSI and POMA data also. Then we also can trigger this DAG manually in the airflow. The Quality reports here as the starting point now covers `Accuracy`, `Completeness` and `Validity`.

***Figure 3: Manually trigger the QC Report DAG***

We also can trigger manually the QC Report DAG by clicking the play button on the dag and fill out the parameters as per Figure 3 listed above. At first we should filled out with `UNLCODE` that we are wanted to check, then the timeline of `start` and `end` timestamp here. After that there are some boolean flag as the parameter above. The boolean flag are listed below:

* `is_poma_included` : this one for include the POMA data into the qc or not.
* `is_csi_included` : this one is for include the CSI data into the qc or not.
* `is_completeness_enabled` : this one is to enable the completeness check to be proceed
* `is_accuracy_enabled` : this one is to enable the accuracy check to be proceed
* `is_validity_enabled` : this one is to enable the validity check to be proceed

Then the `Trigger` button should be click to proceed to the QC Report.

# 2. Architecture Context

The data quality framework operates within the following architecture:

**Airflow**

* Orchestrates data pipelines and executes quality checks as DAG tasks.
* Defines validation steps after data ingestion and before downstream transformations.

**PostgreSQL**

* Serves as the primary data store where validation queries are executed.
* Provides constraints, metadata checks, and SQL-based validations.

**Kubernetes**

* Runs Airflow workers and supporting services in containerized environments.
* Enables scalable execution of quality validation tasks across pipelines.

**Grafana**

* Showing the graphs of the quality reports that we are generating previously.
* Enables us to see the data quality within a months or weekly based on the filters.

Data quality checks are typically triggered at the following stages:

1. **Post-ingestion validation** – verifying raw data integrity.
2. **Transformation validation** – ensuring business logic outputs are correct.
3. **Pre-consumption validation** – confirming data readiness for downstream use.

# 3. Data Quality Dimensions

## 3.1 Completeness

Completeness ensures that **all expected data fields and records are present** within a dataset.

Typical checks are the counts of the source and destinations table check include:

* **API to Staging** this one is to make sure that the data from our source (reads : API) are all that satisfy the requirements is ingested to our Staging Data Warehouse. For example we need to ingest the `Sea Vessel` data from Vessel Voyage that is in completed state (have an end time and also slow moving periods) then this data will be ingested to our data warehose.
* **Staging to ODS** the data transformations from Staging into ODS should have the same counts (e.g if there is 100 visits on Staging then it should be 100 visits also on ODS)
* **ODS to DIM** the transformations from ods into dim tables is usually happen on CSI and POMA data, we are proceeding the ports or ships data then put this one into DIM and the count should be the same from the ODS into DIM (e.g if we are having 4000 ports in ODS that should be 4000 ports in our Dimension tables)
* **ODS to FACT** this is to make sure the counts of ODS to FACT is the same count so it means all of the data from ODS is transformed to FACT.

Example validation logic:

wide1076SELECT
s.count\_stg
, a.count\_api
, coalesce(round(((s.count\_stg::numeric / nullif(a.count\_api::numeric, 0)) \* 100.00), 2), 0)::text AS percentage
FROM stg\_count AS s
LEFT JOIN api\_count AS a
ON s.id = a.id;

Common completeness indicators:

* Percentage of records
* Record counts from source and also destinations

## 3.2 Accuracy / Correctness

Accuracy verifies that **data values correctly represent the real-world entities or processes they describe**.

These checks typically compare values against known business rules or derived expectations. **Accuracy testing** validates that data in **Fact tables** (DATA MART) matches the source data in **ODS tables** (DATA WAREHOUSE). It ensures data transformations from ODS → Fact tables preserve data integrity.

Examples include:

* Summary accuracy checks for example how many berth visits inside the specific terminal.
* Some formula calculation related to the durations checks for example the waiting durations in terminal

Example validation logic in calculated waiting durations in terminal visit:

wide760# Calculate expected waiting duration
df\_with\_calculated\_waiting = df.with\_columns([
(pl.col('anchorage\_during\_terminal\_visit\_duration').fill\_null(0) +
pl.col('slowmoving\_during\_terminal\_visit\_duration')
.fill\_null(0)).alias('calculated\_waiting\_duration')
])
# Find mismatches (tolerance: 0.01)
waiting\_mismatches\_df = df\_with\_calculated\_waiting.filter(
(pl.col('waiting\_during\_terminal\_visit\_duration').fill\_null(0) -
pl.col('calculated\_waiting\_duration')).abs() >= 0.01
)

Accuracy checks may also have a tolerance for allowing some small differences (e.g 36 seconds for duration). But the goal of this checks are to ensure the Fact tables accurately reflect ODS source data.

## 3.3 Validity

Validity ensures that **data values conform to defined formats, types, or allowed domains**.

Typical validation rules include:

* **Non-Null Constraints** are critical fields must have values (not NULL)
* **Non-Negative Constraints** are for numerical fields that should have a positive values e.g duration
* **Logical Order Constraints** are the start timestamps must be before end timestamps
* **Sum Validation** are the calculated total columns must approximately equal the sum of components (with tolerance)

Example validation logic:

wide760for col in BERTH\_VISIT\_DURATION\_COLUMNS:
# Find rows with negative values (excluding nulls)
negative\_df = df.filter(
pl.col(col).is\_not\_null() & (pl.col(col) < 0)
)
invalid\_count = len(negative\_df)
valid\_count = total\_rows - invalid\_count
# Collect invalid rows with their negative values
invalid\_rows = self.\_collect\_invalid\_berth\_visit\_rows(
negative\_df,
value\_column=col
)

Common validity checks include:

* Duration Validity checks
* Timestamp Validity checks
* Validity checks by Domain

  + Port Visit
  + Terminal Visit
  + Berth Visit

# 4. Operational Implementation

Within the pipeline framework:

1. **Airflow DAGs** execute SQL-based validation tasks.
2. Validation results are logged and optionally written to **quality monitoring tables** in PostgreSQL.
3. Failures may trigger:

   * Pipeline retries
   * Alerts
   * Downstream task blocking

# 5. Monitoring and Observability

Data quality outcomes are monitored through:

* **Airflow task logs**
* **Validation result tables in PostgreSQL**

These metrics provide visibility into:

* anomaly detection trends
* pipeline-level data health indicators
