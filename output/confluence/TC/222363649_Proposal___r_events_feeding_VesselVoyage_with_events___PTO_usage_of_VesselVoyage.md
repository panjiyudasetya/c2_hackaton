# Proposal: (r)events feeding VesselVoyage with events & PTO usage of VesselVoyage

**Space:** TC  
**URL:** https://teqplaybv.atlassian.net/wiki/spaces/TC/pages/222363649  

## Content

## VesselVoyage event processing

| **Event type** | **Result** | **(r)events component** | **Additional requirements** |
| --- | --- | --- | --- |
| `AnchorEvent` | * starts visit, if in voyage * adds to `Visit.anchorAreas` | * anchor-monitor |  |
| `DestinationChangedEvent` | * update `Entry.dest` | * ais-diff |  |
| `EtaEvent` | * update `Entry.eta` | *none*  AIS ETA is not used for this only (dynamic/non-deterministic) ETAs from other systems: `port, berth, pilotBoardingPlace, nomination, lock` | * requires external/non-revents components to publish ETAs, VesselVoyage can’t get these from (r)events |
| `EncounterEvent` | * update `Entry.esof` (encounters) | * encounter-monitor |  |
| `MovementEvent` | * update `Entry.esof` (stops) | * ais-diff | * ship trace * berths by location * anchorages by location |
| `PortEvent` | * starts visit, if in voyage * adds to `Visit.portAreas` | * area-monitor | * find port by id * find anchorage * find CSI ship register by IMO |
| `StatusChangedEvent` | * update `Entry.esof` (stops) | * ais-diff |  |
| `UniqueBerthEvent` | * update `Entry.esof` (stops) * update `Visit.berthAreas` | * berth-monitor *not ready for (r)events yet* | * find berth by id * ship trace * berths by location * anchorages by location |

## PTO VesselVoyage usage

| **Request** | **Usage** | **Resolve** |
| --- | --- | --- |
| `getVisitedPorts` | Charter reports: get all ports that the `imos` were in. | Filters on `parameters.ports` containing the visited port as well.  Why not just use `parameters.ports`? |
| `getData` | Requests visits. | Should be done after (r)events has run. |
| `getVisits` | Used in tandem with `getData`.  Checks whether `visitExistsInMiddle`.  Determines if two visits are the same. |  |
| `fetchPreviousVoyage` | Used in tandem with `getData`.  When visits are merged there is a check if it’s about the same visit, and then the previous voyage is requested. | Could use `fetchVoyagesOfVisits` earlier to not request them here per ship. |
| `fetchVoyagesOfVisits` | Used in tandem with `getData`.  Pairs the visits with the voyages, and creates the report. |  |

Other comments:

* `esof.stops` are used (both voyage+visit)
* `Visit.anchorAreas` (whether visit has ended, `visit.finished` can be used instead)
* `Visit.berthAreas` (whether visit has ended, `visit.finished` can be used instead)

## Preliminary conclusion

Most events that VesselVoyage relies on can be generated by (r)events.  
Only the ETA events can’t (currently) be generated there. The ETA events for `port, berth, pilotBoardingPlace, lock` could technically be generated as part of the (r)events process, but is this desirable? The `nomination` ETA events can’t be generated, since they come from nominations.

PTO uses VesselVoyage, but this dependency is considerably light.  
It has three main usages of VesselVoyage:

* Get the ports that ships were in

> Can be requested from (r)events after it has run.

* For two visits, checks if there are visits in between. If any visit in between is for a port that doesn’t equal the one of the first visit, then the visits are not merged and are considered different/not the same.

> Can be done purely by (r)events, but requiring: the EOS to be set with a large enough size, and the margin (of 2w default) to be used.
>
> Then there is the guarantee that the ship left the port for at least 2 weeks (by default), and it didn’t enter the port again within 2 weeks. Meaning the ship hasn’t entered the same port again after 4 weeks. This should be pretty conclusive that the visit is not the same, even when not knowing if the ship actually went to a different port.
>
> But, then the ship could still have entered another port within this 4 weeks. PTO can check that after the EOS/port area exit of the relevant port there is no port entry event for another port that is not considered the same.

* Stops of the visits and the previous voyages.

> (r)events doesn’t currently contain these stops. This can be solved in three ways:
>
> - recalculate VesselVoyage based on the additional events generated by (r)events
>
> - let VesselVoyage run as part of the (r)events process to generate these stops then
>
> - stop using VesselVoyage, generate (new) reliable movement/stop events, and use those

## Possible directions to take

* feed VesselVoyage with (r)events data, to be used by PTO  
  *requires a VesselVoyage lite instance to be run as part of (r)events, if not merging data back and recalculating all relevant vessels*
* stop using VesselVoyage in PTO and fully rely on (r)events, including the new movement/stop event  
  *(see the feeding of data into VesselVoyage as a separate thing that can be done in parallel/later)*

## Advise / preferable direction

Berth events are generated by the area-monitor. Confirmed and unique berth events, as generated by the berth-monitor, are not available since it’s not yet ready to run during (r)events. This should be one of the first steps to fix before considering the next steps. Since VesselVoyage relies on this data, and PTO relies on this data via the stops of VesselVoyage.

I imagine rewriting/refactoring parts of VesselVoyage to be a lighter variant to be run in some part of (r)events will be quite some work to do in the short-term. Especially since currently VesselVoyage requests ship history when creating those stops on visits/voyages.

It seems like PTO is not heavily tied to using VesselVoyage. Combining that with the want for having less logic and fallbacks in place in PTO to fix issues that could/should have been solved by the respective component. For most of the usages (r)events could be utilized to solve these issues. When also having the berth-monitor and the new (already proposed) stop/movement events

**Concrete first steps (PTO):**

* make berth-monitor ready for (r)events
* make a component that mimics the behavior of the VesselVoyage stops, but allowing for streaming of data as part of the (r)events process  
  *(Which would allow for PTO to be independent of VesselVoyage, and also for VesselVoyage to be fed based on these events. Without needing to spend much effort on refactoring VesselVoyage first, taking the lessons learned from the VesselVoyage stops though.)*
* make PTO not dependent on VesselVoyage, only using (r)events  
  *(This makes the whole process deterministic, only based on the ship history itself and the context data as part of POMA and CSI.. Ensuring the data is as perfect, using the latest insights, it can be. While also being able to use this same data as a base to feed VesselVoyage.)*

**Concrete later steps (VesselVoyage):**

Once the above steps are done, the following steps could help to get VesselVoyage richer in terms of data quality.

We should envision further what exactly we want here. We’ve been discussing about merging the events as detected by (r)events back into event-history.

However, I can imagine us constantly adding more context info. Being either context in terms of CSI info, or POMA being extended to have more data or facilitate in new data models to map infrastructure in another way. Assuming that this is the case, how would running (r)events once for a subset of the world solve for these changes? To me it seems like it should be more of a structural approach. Not influenced by the reports that are ran by PTO, but by what context is changed.

I propose to plan and envision how (r)events is going to concretely relate to VesselVoyage. But not strictly being related to the steps taken as part of PTO.
