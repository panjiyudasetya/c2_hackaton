# 3rd party notification interaction

**Space:** TC  
**URL:** https://teqplaybv.atlassian.net/wiki/spaces/TC/pages/36929537  

## Content

Not all parties that have to interact with a nomination are expected to have an account in FB. To allow them to interact with a nomination, we want to develop a system with which “magic links” can be sent via email that allow the recipient to perform basic operations with the nomination for a limited amount of time. When developed, this functionality will allow the following:

* An email is sent to a 3rd party. The mail contains a button similar to the normal notification mail, which allows the recipient to open the nomination in FuelBoss
* When clicking the button, a limited view of FuelBoss is opened in the user's browser, in which only the relevant nomination is shown.
* In this limited view, a truck company can accept/decline the nomination
* Agents can edit the eta/etd of their respective vessel (receiving vessel for customer agent contact, bunker vessel for supplier agent contact)
* Other company types currently will **not** receive a mail with clickable button, as there are no interaction requirements

In particular, the user cannot submit a counterproposal.

* After a certain amount of time, the “magic link” expires, and the recipient can no longer access the nomination in FuelBoss. For trucking companies, the link will have a validity of 24h, for agent companies, the link will expire 24h after the BST at the time of sending of the email.

### Implementation challenges

There are two implementation challenges associated with this user story: the “magic link” and the limited user interface.

The “magic link” will contain some kind of (JWT?) token generated and signed by the Teqplay backend. The token includes the user name, mail address, role and event id relevant to the notification. It is generated and signed by the Teqplay backend, but it should also be accepted by the FuelBoss backend for some requests. This means that both backends should have a shared secret for verification of the token, or a public/private key setup should be used where the FuelBoss backend knows the public key.

Based on the token, the backend grants access only to the nomination with the event id contained within the token, and with data associated with that nomination.

For the limited user interface, a specific landing page should be created that only shows a single nomination, based on the event id in the URL. It should not be possible to access the rest of the frontend user interface (the token also disallows any calls needed to the relevant backends)

### Backend tasks

**Generate/validate token (12h)**

For a specific 3rd party contact and nomination, generate a token containing all relevant details. Update authentication code to accept such tokens, and update all the permission checks to grant access to the nomination referenced in the token and all referenced objects (ship, bunker ship, etc).

Tokens for trucking companies should expire after 24h, tokens for agent companies should expire 24h after the current BST. The expiration time is always fixed, if the BST is updated, tokens issued prior to that can not be amended.

**Include user-specific token in notification emails (8h)**

Instead of sending one personalized email to multiple 3rd party recipients, update the code such that every recipient gets its own personalization including the magic link.

**Update nomination model (6h)**

Add fields to the nomination model to record accept/decline action of truck operators, including time of acceptance and user name. Agent ETA updates will be stored in the normal ETA fields of the nomination.

### Frontend tasks

**Hide buttons/actions (4h)**

Buttons and actions that are not accessible based on the permissions in the token should be removed. Also, the history navigation should be removed.

**Adapt permission checks to special token (8h)**

Adapt the permission checks to account for the special token. Instead of checking by user role, the actual token should be inspected.

**Add fields (8h)**

Show accept/decline details of truck operators when viewing the nomination. Includes time of acceptance and user name.

### DNV tasks

**Validate token**

The backend should be able to validate the token generated by the Teqplay backend, and it should be accepted by any relevant backend calls.

Note: it could be the case that the frontend only needs to make calls to the Teqplay backend, which would simplify things a lot.

**Nomination-only frontend**

Frontend route that shows the latest state of a single nomination based on the event id in the supplied url.
