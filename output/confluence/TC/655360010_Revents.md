# Revents

**Space:** TC  
**URL:** https://teqplaybv.atlassian.net/wiki/spaces/TC/pages/655360010  

## Content

**Revents** is designed to re-run the **AIS Engine** event monitors on historical AIS data.

It allows users to generate new events based on updated monitor logic, ensuring that event detection aligns with the latest rules and improvements. This enables users to review historical data with the most current event-monitoring criteria.

## **High-Level Architecture**

Revents is a core component of the `ais-engine` project, designed to allow users to create scenarios through the Revents API. A scenario request enables users to retrieve re-generated historic events that occurred within a specified time window for one or more ships.

When a scenario request is submitted, Revents processes it by:

1. **Defining Scenario Settings** – Various parameters can be configured in the request, as outlined in the API's README.
2. **Resolving Interests** - Resolves the requested interest (the subject for the event regeneration). This can be a specific mmsi, a list of mmsi’s or an area
3. **Initializing Event Monitors** – Revents spins up multiple event monitors to analyze historical AIS data from the specified time period.
4. **Generating Events** – These monitors process AIS data to identify and generate relevant events.
5. **Storing Events** – The generated events are stored in the Revents database.
6. **Returning Results** – Users can then retrieve these stored events via the API.

This allows the user to generate events based on the current logic of the event-monitors which allows for improvement in event quality.

### **Architectural diagram**

### **Architectural Overview**

The Revents system consists of multiple components that work together to generate, process, and store ship-related events based on historical AIS data. Below is an overview of its architecture:

### **Core Components**

`revents-engine-api` acts as the orchestrator for event generation. It determines which ships have visited specified locations when we get location-based scenario requests, provisions and manages necessary nodes/applications.

`revents-engine` retrieves historical AIS data, processes it into differential (diff) events, and distributes them. Various monitors analyze these diff events to generate ship-related events.

`revents-orchestrator`aggregates ship events from the monitors and stores them in the database for retrieval.

`vesselvoyage` *(optional component)* runs as part of the Revents processing pipeline, transforming generated events into visit and voyage changes.

### **External Connections**

`poma` is used to retrieve area data for the area/anchor monitor and to resolve area IDs.

`csi` Provides ship-related information, including details about nearby service vessels.

`ship-history` retrieves AIS history points based on area and MMSI.

### **High-level life-cycle**

1. **Scenario Creation and Scheduling:**

   * The user creates a scenario and schedules it via the `revents-engine-api`.
2. **Interest Resolution:**

   * The `revents-engine-api` resolves the user's interests. Depending on the volume of interests, the system may split the scenario into multiple parallel processes to optimize execution.
3. **Scenario Storage:**

   * The scenario is stored in the database, where it is picked up by the `revents-engine-orchestrator`.
4. **AWS Instance and Kubernetes Job Deployment:**

   * The `revents-engine-orchestrator` provisions an AWS instance and deploys a Kubernetes job containing the following core components:

     + `ais-diff`
     + `event-monitors`
     + `revents-engine`
     + `vesselvoyage` *(optional)*
5. **Scenario Execution:**

   * Once all core components are ready, the `revents-engine-orchestrator` triggers the `revents-engine` to start the process.
   * The `revents-engine` manages the scenario execution, while the `revents-engine-orchestrator` monitors progress, collects the generated events, and stores them in the database.
6. **Completion and Shutdown:**

   * Upon completion, the `revents-engine` signals the end by sending poison pills to all other components, which in turn send their own poison pills.
   * The `revents-engine-orchestrator` receives all poison pills and acknowledges receipt, signaling the `revents-engine` that all components have completed.
7. **Tear Down Process:**

   * After the `revents-engine` signals it’s finished, the `revents-engine-orchestrator` dismantles the Kubernetes job and terminates the AWS instance.
8. **Event Retrieval:**

   * Once the tear-down process is complete, the generated events can be requested via the `revents-engine-api`.

## Life cycle of the Process

**Revents Process and Scenario Scheduler**

The **revents** process is managed by the **Scenario Scheduler**, which monitors all active scenarios and ensures the execution of required phases. Below is a high-level overview of how the scheduler operates. The scheduler runs both in the `revents-engine-orchestrator` and `revents-engine-api` part of **revents**, both picking up different phases of the process.

1. The scenario is initialized, and settings are adjusted based on predefined guarantees (e.g., specific system configurations like vessel voyage). These settings are validated and applied to the scenario.
2. The **Scenario Scheduler**, which manages all active scenarios, iterates through each scenario.
3. The scheduler attempts to execute the current phase. If the phase completes successfully, it moves to the next phase. If not, it re-executes the current phase until completion.

**Scenario Phases**

The flowchart below illustrates the different phases the **Revents Scenario Scheduler** progresses through, starting from the **Queued** phase and ending at either **Finished** or **Crashed**, depending on the scenario's outcome.

1. The interests are resolved by mapping the specified areas to ships using the `ship-history` Area Index. This process collects all the ships that were in the area during the given time window, resulting in a list of ships.
2. The system checks the size of the interest. If it exceeds the maximum allowable amount, the scenario is forked into several smaller scenarios that can run in parallel.
3. A job is created in Kubernetes, which spins up a pod containing all the necessary containers for the scenario.
4. The `event-stream` and, optionally, the `vesselvoyage-change-stream` are set up. The orchestrator starts consuming the events returned from the event monitors and vesselvoyage inside the pod. A thread is initiated to keep consuming these messages from the NATS stream until a poison pill is published.
5. The consumer continues to process the events and saves them into scenario-specific collections. Each scenario has its own collection for monitor events and vesselvoyage changes.
6. Vesselvoyage post-processing involves storing the interests of the scenario in a format compatible with vesselvoyage. These interests are saved in the database, where they can be requested using the `revents-engine-api`. The interests are used on the vesselvoyage side to merge the vesselvoyage changes generated by revents.

### VesselVoyage Recalculation Process

On the **vesselvoyage** side, visits and voyages can be recalculated using **revents**. Below is a flowchart illustrating the logic used for the recalculation process on the **vesselvoyage** side.

1. The **vesselvoyage** API can request a recalculation with **revents** based on a single IMO or a list of IMOs, or it can recalculate for an entire port (unlocode).
2. The time windows of the request are expanded to align with the nearest voyage start and end times, ensuring that the visit within the time window can be properly replaced.
3. The merge entries from **revents** are used to overwrite the original **vesselvoyage** visit and voyage data, replacing the entries with the recalculated visit and voyage changes.

## Error handling & Debugging

**Running Locally**

There is documentation available in the README of revents as to how run revents locally. But its very hard to do currently because of the memory requirements (16+ GB) to run revents.

#### **Common Issues**

* **Model Misalignment**: A mismatch between **AIS-Engine VesselVoyage models** and **VesselVoyage models** can prevent certain entries from merging back correctly. Ensure that Revents uses the same version as the currently deployed VesselVoyage version to avoid misalignment issues.
* **Merge Errors**: Revents may throw errors when it cannot merge back entries. This is often caused by:

  + Corrupted original VesselVoyage data, resulting in no data to replace.
  + Extremely large visits where the merge-back data does not cover the entire visit, preventing proper replacement.  
    A retry mechanism is in place to recalculate the entire visit, which helps resolve issues caused by large visit sizes.
* **Outdated Ship History Area Index**: If the **Ship History Area Index** is not up to date, monitors may not receive data, leading to almost zero events for the recalculated period. Ensure that the index is regularly updated to prevent this issue.
