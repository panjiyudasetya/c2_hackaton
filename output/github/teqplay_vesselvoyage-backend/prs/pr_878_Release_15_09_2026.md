- `d71fb1d7` **Joost Dambrink** (2026-09-03): Speed up the revents merge-back for scenarios with many ships
  Merging a scenario back fetched the scenario's FULL interest list from
  revents once per ship, only to keep one ship's slice - quadratic in the
  number of ships. The interests are now fetched once per merge
  (ReventsReplayMergeService.fetchInterestsByShip, cached per scenario by
  ScenarioInterests) and each ship gets its slice handed into
  buildMergeEntries.
  
  Further merge-step wins:
  - persistMergeResultV2 now passes the overwritten entries as the
    PreviousEntryVersions diff baseline instead of NONE. The merge and the
    persist run under the ship's lock, so those are still exactly the
    stored versions; persistence no longer re-fetches every entry's stored
    children before diffing (2 reads per entry, inside the live-processing
    lock).
  - Scheduling post-processing for a ship's changed entries is one bulk
    write (PostProcessableDataSource.saveAll) instead of one save round
    trip per entry.
  - recalculation.merge-ship-threads default raised from 4 to 8; the
    fetch/replay part of a ship's merge holds no locks and doesn't touch
    live collections, so the old throttle was stricter than needed.

  Claude-Session: https://claude.ai/code/session_01UaaGLZMjwoHZVbM7TGMn6z

## Review Comments

### Copilot — 2026-09-15 on `src/main/kotlin/nl/teqplay/vesselvoyage/service/recalculation/ReventsConversionService.kt`

This re-enables the behavior that the previous setting explicitly disabled: with S2S ports, distributed interests can contain the same ship/event in multiple jobs. `fetchInterestsByShip` then replays every resolved interest, while the merge path only deduplicates entries within one replay window, so the same port visit can be persisted/published more than once. Please keep distribution disabled until cross-interest deduplication is in place, or restrict it to scenarios where S2S duplication cannot occur.

### Copilot — 2026-09-15 on `src/main/kotlin/nl/teqplay/vesselvoyage/service/recalculation/ReventsRecalculationService.kt`

These snapshots are not guaranteed to be the stored versions: PostProcessingService persists entries/ESoFs without taking ShipLockService. A queued post-processing task can update an overwritten ESoF after merge loaded it but before this call, so using the stale wrapper as previousVersions can make normalized child diffs miss concurrent children and overwrite the newer ESoF. Use a current baseline under a lock shared by all writers, or retain PreviousEntryVersions.NONE until that synchronization exists.
