## Description

## What

`createScenarioRequestForPort` no longer sets `useInterestDistribution = false` — port recalculation scenarios now use revents interest distribution, so the port's resolved ships are forked over multiple parallel revents jobs.

## Why

Port recalculations are bottlenecked by single-job monitor throughput (encounter-monitor / area-monitor consume the replay single-threaded). ais-engine now forks a scenario into `ceil(interests / 100)` child jobs, capped at 5 (teqplay/ais-engine#1583), and each fork independently resolves the encounter-relevant service vessels, so child jobs are self-contained. Port recalculations are the main flow this is meant to speed up, so the explicit opt-out here blocked the whole point.

## Trade-off (accepted for now)

The old `false` carried a comment: interest distribution "result[s] in duplicate visits when having S2S ports" — two ships in an S2S transfer can land in different forks and each generate a visit. This is knowingly accepted for now to get the parallel speedup; the duplicate-visit handling at S2S ports can be revisited separately.

## Notes

- `ReventsConversionServiceTest` updated to expect `useInterestDistribution = true`.
- Behaviour only changes when the port resolves to more than 100 ships in the window (the ais-engine fork threshold); smaller ports keep running as a single job.
- Tests could not be run in the sandbox this was authored in (no credentials for repo.teqplay.nl) — CI is the verification.
