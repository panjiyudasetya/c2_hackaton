## Description

## Problem

Restarting VesselVoyage fully restarts the merge process of a recalculation. `ReventsRecalculationService` only persists merge progress as counters (`PhaseProgress(completed, total)`), never *which* ships were merged. After a restart, `init()` re-queues every non-final scenario and the next tracking pass runs the whole merge again from ship 0 — re-fetching, re-replaying, re-persisting and re-publishing every ship that had already merged. For large port scenarios that means hours of duplicated work (and duplicate downstream publishes).

The same applied to a pass that ended in `RETRY_LATER`: the retried pass re-merged every ship, including the ones that had already succeeded.

## Fix

Record each ship on the recalculation document as its merge-back completes, and skip those ships when the merge of the scenario is picked up again:

- **`RecalculationResult`** (api): new `mergedShipIds: List<String>` field (default empty, so existing documents deserialize unchanged) on the interface and all five result types.
- **`ReventsRecalculationsDataSource.addMergedShipId`**: atomic `$addToSet` per finished ship, so concurrent ship threads and an interruption at any point stay consistent. It deliberately does not go through `updateStatus`, which rewrites the whole `revents` subdocument.
- **`ReventsRecalculationService`**:
  - `mergeShipsOfScenario` and `runMergeScenario` (merge-only scenarios) filter out already-merged ships and record each ship as it finishes — except ships that returned `RETRY_SCENARIO_LATER`, which must be attempted again.
  - `MergeProgressReporter` takes an `initialCompleted`, so the progress bar resumes from where it was instead of jumping back to 0.
  - `mergeFinishedScenario` seeds its error collector with the errors persisted so far: ships merged before the interruption no longer re-report their warnings on resume, so without this the final phase (e.g. `PARTIALLY_FAILED`) could be computed from an incomplete error list. (`runMergeScenario` already seeded this way.)

`mergedShipIds` is kept on the document after the merge finishes, like `expectedShipIds`, for inspection.

## Known trade-off

The merge-failure summary and before/after summary statistics are collected in memory per merge run, so after a restart they only cover the ships merged since the resume. That information was previously "complete" only because everything was re-merged; keeping those collectors restart-proof would need a persisted per-ship breakdown and felt out of scope for this fix.

## Testing

Added unit tests covering: ships recorded as they finish, already-merged ships skipped on resume (including resumed progress reporting), `RETRY_SCENARIO_LATER` ships not recorded, persisted errors kept in the final status, and resume of merge-only (`.MERGE`) scenarios.
