## Description

Consumer side of [teqplay/ais-engine#1573](https://github.com/teqplay/ais-engine/pull/1573), which is merged and released. Maps the monitoring data (r)events now reports about a running scenario onto `ReventsRecalculationStatus`, and records when a recalculation is completely finished on this side. The front-end that surfaces it is [teqplay/vesselvoyage#165](https://github.com/teqplay/vesselvoyage/pull/165).

## What is added

| Field | Meaning |
|---|---|
| `reventsFinishedAt` | When (r)events finished the scenario and its events became collectable |
| `finishedAt` | When this scenario was completely finished, *including* the merge back into VesselVoyage |
| `monitors` | When the monitors in the (r)events job became ready, when AIS data actually started flowing to them, and when each one stopped |
| `aisReplay` | The throttled AIS publish rate feeding those monitors, plus each monitor&#39;s AIS queue depth |

`reventsFinishedAt` and `finishedAt` together split the total turnaround into the time spent in (r)events and the time spent merging back — the thing that was previously impossible to see.

## Notes on the implementation

**`finishedAt` stamping.** The status is rebuilt from the (r)events response on every poll, so it can&#39;t simply be carried forward. A private `withFinishedAt` helper stamps it the first time the scenario reaches a final phase and never moves an existing stamp — applied at each of the four places a terminal status is written (`checkScenarioProgress` crash and merge-complete paths, `runMergeScenario`, and `stop()`). `trackScenario` reads the stored value so re-tracking a finished scenario doesn&#39;t make it appear to finish twice.

**Locally mirrored metric types.** `Monitors` and `AisReplay` are defined in this repo rather than reusing ais-engine&#39;s `AisPublishThrottle` / `AisQueueDepth`. That is deliberate: the `api/` module pins its *own* `aisengine_version` (`master-2.8.0`), far older than the root module&#39;s, so reusing those types there would not resolve. Mirroring also keeps the published `client` artifact independent of which ais-engine version the application module happens to use.

**Queue depths are batch counts.** `messages` counts RabbitMQ messages, each carrying a batch of AIS messages; `estimatedAisMessages` is the same depth in AIS messages, assuming full batches (true for all but the last batch of a drain). Both this and `aisMessagesPerSecond` follow the simplification agreed in review on the ais-engine side.

## Dependency

`aisengine_version` is `20260819-b1593.1` — the master release of #1573 (run 1593, "Release 19/08/2026"). This replaces the mutable `20260818-SNAPSHOT` the branch was pinned to while #1573 was open, so the earlier "do not merge on a snapshot" caveat no longer applies.
