## Commits

- `eae791a8` **Claude** (2026-09-03): Resume an interrupted recalculation merge instead of restarting it
  A restart of VesselVoyage re-merged every ship of an in-flight scenario
  merge from scratch: only the completed/total counters were persisted,
  not which ships had already merged. Record each ship on the
  recalculation document as it finishes merging (atomic $addToSet) and
  skip those ships when the merge is picked up again, so a restart - or a
  pass that had to be retried later - continues where it left off.
  
  The final status also seeds the error collector with the errors
  persisted so far, since skipped ships no longer report their warnings
  again on resume.
  
  Co-Authored-By: Claude Fable 5 <noreply@anthropic.com>
  Claude-Session: https://claude.ai/code/session_019SK1ELqeTfLLPQMqrriFYi
- `139b5ec6` **Claude** (2026-09-03): Key merge-only resume tracking by source scenario and ship
  A merge-only recalculation may merge the same ship from several source
  scenarios. Recording completion by ship id alone would skip every entry
  of that ship once one source finished, silently dropping the others on
  resume. Merge-only scenarios now record "<source scenario id>:<ship id>"
  keys instead.

<summary>Pull request overview</summary>

This PR improves recalculation merge resilience by persisting per-ship merge completion, allowing interrupted merges (e.g., restarts) to resume without reprocessing already-merged ships, while preserving previously-recorded merge errors.

**Changes:**
- Persist each successfully merged ship ID (`mergedShipIds`) and skip already-merged ships when resuming a merge.
- Seed merge error collection from persisted status so prior ship-level errors aren’t lost after an interruption.
- Add unit tests covering resume/skip behavior for both regular scenarios and merge-only scenarios.

### Copilot — 2026-09-03 on `src/main/kotlin/nl/teqplay/vesselvoyage/service/recalculation/ReventsRecalculationService.kt`

`progress.shipFinished()` is currently called even when the ship returns `RETRY_SCENARIO_LATER` and is *not* recorded in `mergedShipIds`. This can persist merge progress beyond the number of actually-merged ships, so when the merge resumes (based on `mergedShipIds`) the progress can jump backwards.
