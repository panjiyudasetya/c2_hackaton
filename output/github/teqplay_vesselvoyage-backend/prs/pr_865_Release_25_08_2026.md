- `8ab1c8a4` **Claude** (2026-08-17): Surface revents monitoring metrics on the recalculation status
  Maps the monitoring data (r)events now reports about a running scenario
  onto ReventsRecalculationStatus, and records when a recalculation is
  completely finished on this side.
  
  - reventsFinishedAt: when (r)events finished the scenario and its events
    became collectable.
  - finishedAt: when this scenario was completely finished, including the
    merge back into VesselVoyage. Together the two split the total
    turnaround into the (r)events part and the merge-back part.
  - monitors: when the monitors inside the (r)events job became ready,
    when AIS data actually started flowing to them, and when each of them
    stopped processing.
  - aisReplay: the throttled AIS publish rate feeding those monitors, and
    the depth of each monitor's AIS queue - both in RabbitMQ messages and
    scaled to AIS messages, since one RabbitMQ message carries a batch.
  
  The status is rebuilt from the (r)events response on every poll, so
  finishedAt is stamped when the scenario first reaches a final phase and
  an existing stamp is never moved.
  
  The metrics types are mirrored locally rather than reusing the ais-engine
  model, keeping the published api module independent of the ais-engine
  version the application module uses.
  
  NOTE: requires an ais-engine release containing the matching change, and
  aisengine_version in build.gradle bumped to it. Until then the mapping in
  ReventsConversionService does not compile - ScenarioResponse.finished,
  Status.aisPublishingStarted, Status.publishThrottle and Status.aisQueues
  do not exist in 20260729-b1494.1.

- `0c3b2cdb` **TeqJoostD** (2026-08-18): Split revents recalculation phases and add merge and post-processing progress
  A recalculation used to jump from PROGRESSING straight to its final phase, so
  everything after the revents run itself — merging the generated events back and
  post-processing the merged entries — was invisible, and the scenario was already
  reported as FINISHED while its entries were still being post-processed.
  
  The phases are now QUEUED, RUNNING_REVENTS (was PROGRESSING), MERGING,
  POST_PROCESSING and the three phases a scenario can end in: FINISHED,
  PARTIALLY_FAILED and STOPPED, which are marked as final on the enum itself.
  
  Merging counts the ships it merged, post-processing counts the entries it
  post-processed, and both are persisted while they run. The phases follow each
  other, so only the counters of the current phase are kept and `progress` reports
  that single phase: the front-end renders one progress bar that follows the
  scenario, never a merge and a post-processing bar at the same time.
  
  A scenario stays tracked until its merged entries are post-processed, and gets
  its final phase from what the merge ran into. Entries that keep failing to
  post-process no longer keep it out of a final phase forever: after
  `recalculation.post-processing-stall-timeout` it finishes anyway and reports it.
  
  Recalculations stored with the old PROGRESSING phase are migrated, and the phase
  also reads back through a Jackson alias.

- `34567830` **Darius Wattimena** (2026-08-19): Fix driftingPending never resolving for unchanged merge entries
  A revents merge-back registered every recalculated entry as pending
  post-processing in the per-ship change statistics, but TCC-1121 stopped
  scheduling post-processing for entries the replay reproduced identically.
  Those entries never publish an EndPostProcessingEvent, and that event is
  the only thing that clears pendingEntryIds - there is no sweeper or
  timeout - so driftingPending stayed true forever.
  
  The skip is content-based, so it lands almost exclusively on voyages: a
  NewVoyage is a far thinner document than a NewVisit, so the replay
  reproduces it byte-identically far more often. Observed on a scenario
  where 19 of 25 ships were wedged, every stuck id a .VOYAGE.
  
  recordMerge is now handed changedNewEntryIds - the ids that are actually
  scheduled below it - instead of all of them.
  
  Two related defects in the same path made the drifting counts that did
  resolve wrong:
  
  - An ESoF can be postProcessed with slowMovingPeriods left null when
    post-processing found no drifting at all. The calculator read that null
    as "not post-processed yet", so a single such entry made its whole side
    unknown. Knownness now keys on postProcessed.
  
  - The unknown side was then flattened to "no drifting" with orEmpty() on
    the previous side only, so every period of the other side read as an
    addition. Both sides are now nullable and a window whose drifting
    cannot be established is skipped with a warning instead of compared
    against an incomplete other side.
  
  - An unchanged entry sits in both overwritten (finalized, with periods)
    and recalculated (replayed, without), and never reports back, so its
    periods read as removed. The calculator now reads the drifting of an
    entry that will not be post-processed again from the entry it replaced.
  
  Co-Authored-By: Claude Opus 5 <noreply@anthropic.com>
