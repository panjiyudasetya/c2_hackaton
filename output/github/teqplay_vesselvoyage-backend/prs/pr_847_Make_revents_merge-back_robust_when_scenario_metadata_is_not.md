## Description

## Problem

Large merge-back scenarios failed intermittently with `REQUEST_FOR_INTERESTS_FAILED`, while smaller scenarios worked fine. The revents backend answered the interests/entries requests with:

```
400 Bad Request — "Merge-back metadata for scenario '…' is not prepared.
Call POST /vesselvoyage/v2/{id}/merging/prepare first."
```

## Root cause

After a recalculation scenario reaches its final phase, the scheduled `checkScenarioProgress()` immediately asks revents for the interests/entries to merge. For **bigger scenarios**, revents' preparation of that merge-back metadata lags behind the scenario reaching its final phase, so the first request arrives before revents is ready and gets a `400`. Smaller scenarios are prepared almost immediately, which is why they kept working.

`isRetryableMergeFailure()` only treated a `503` as transient; the `400 "not prepared"` fell through to the unrecoverable branch, which recorded `REQUEST_FOR_INTERESTS_FAILED` and abandoned the whole merge-back — with no way for data-env consumers to retry.

## Change

- `ReventsRecalculationService.isRetryableMergeFailure()` now also treats a `400` whose body indicates the metadata *is not prepared* (matched on the stable message markers `"is not prepared"` / `"merging/prepare"`) as transient.
- The scenario is kept queued (`RETRY_LATER`) and retried on the next scheduled progress check, converging once revents has finished preparing.
- Covers both merge paths: `getShipIdsForMerging` (interests) and `buildMergeEntries` (entries).
- Any *other* `400` remains unrecoverable, so genuine bad requests still surface.

## Tests

Added three unit tests mirroring the existing `503`-retry tests:
- recalc→merge path retries on "not prepared" and then succeeds with no error;
- a generic `400` still reports `REQUEST_FOR_INTERESTS_FAILED` (not retried);
- the merge-scenario path retries on "not prepared" and then succeeds.

## Notes

- **CI should be the source of truth for the build.** The teqplay dependencies resolve only from the credentialed `s3://repo.teqplay.nl` Maven repo, which isn't reachable in the dev environment used to author this change, so `./gradlew test`/`ktlintCheck` could not be run locally. The change was verified by close review against the retry tests it mirrors.
- Retry is unbounded (once per scheduled pass) — consistent with the existing `503` behavior. Happy to add a bounded retry with a hard failure after N attempts if preferred.
- The synchronous `POST /scenario/{id}/merge` path is left returning an error on "not prepared", since it is user-triggered and can be retried via the API.
