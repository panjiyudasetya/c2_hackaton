# PR #873: Speed up the revents merge-back for scenarios with many ships

## Description

Merging a revents scenario back into production data was very slow for big scenarios (port recalculations with thousands of ships). This PR removes the structural bottlenecks in the merge step itself.

## What was wrong

**Interest fetching was O(N²).** `ReventsReplayMergeService.buildMergeEntries` started every ship's merge with `getInterests(scenarioId)`, which returns the scenario's **full** interest list — and then kept only that one ship's slice. A scenario with N ships transferred and deserialized N whole interest lists from the revents API.

**Persistence re-read what the merge already held.** `persistMergeResultV2` passed `PreviousEntryVersions.NONE`, so the normalized-children diff (`saveForEntry` for stops/area activities/ESoF children) re-fetched every entry's stored children from Mongo before diffing — two extra reads per entry, inside the `ShipLockService` lock that live AIS processing contends on. The merge already holds those stored versions in `mergeResult.overwrittenEntries`.

**Post-processing scheduling wrote one document at a time.** Each changed entry of a ship was a separate `postProcessable` save round trip.

## Changes

- `ReventsReplayMergeService.fetchInterestsByShip(scenarioId)` fetches the interest list once and groups it by ship; `buildMergeEntries` now takes the ship's interests as a parameter. A per-merge `ScenarioInterests` cache in `ReventsRecalculationService` (`ConcurrentHashMap.computeIfAbsent`) makes each scenario's list get fetched exactly once, including for merge-only scenarios whose ships span multiple source scenarios. A failed fetch is not cached, so the existing retryable-failure handling (`RETRY_SCENARIO_LATER` / `REQUEST_FOR_ENTRIES_FAILED`) is unchanged.
- `persistMergeResultV2` builds `PreviousEntryVersions.fromEntries(...)` from the overwritten entries and hands it to `persistAndPublish` and `persistAndPublishUnchangedRecalculation` (new optional parameter, defaulting to `NONE` for other callers). This is safe because the merge and the persist run under the ship's lock, so the overwritten entries are still exactly the stored versions; ids not covered (boundary entries, new ids) keep the existing fetch fallback.
- `PostProcessableDataSource.saveAll` bulk-upserts, with a new `PostProcessingService.schedulePostProcessing(entryIds, scenarioId)` overload; the merge path and the existing `Set` overload both use it. Trace scheduling needed no change (in-memory set).
- `recalculation.merge-ship-threads` default raised 4 → 8 (both the Kotlin default and `application.properties`). The dominant per-ship work — fetching events and replaying them — holds no locks and touches no live collections, so the old throttle was stricter than its purpose required.

## Tests

- `ReventsReplayMergeServiceTest`: calls updated to the new signature, plus a test for `fetchInterestsByShip` grouping.
- `ReventsRecalculationServiceTest`: all `buildMergeEntries` stubs/verifies extended to the new parameter, default `fetchInterestsByShip` stub, post-processing verifies switched to the bulk call.

`saveAll` assumes the bulk operations target disjoint documents (unordered bulk write), but it doesn't enforce uniqueness by `_id`/`entryId`.
