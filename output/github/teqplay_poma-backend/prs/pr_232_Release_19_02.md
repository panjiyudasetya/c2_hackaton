## Review Comments

### Copilot — 2026-02-16 on `src/main/kotlin/nl/teqplay/poma/feature/mapping/MappingService.kt`

New mapping endpoints/services introduce non-trivial behavior (aggregation counts, filtering by expectedMappingStatus, pagination calculations). There are existing service/unit tests in the repo; consider adding tests covering: (1) overview counts with missing/null status, (2) pagination boundary conditions, and (3) filtering by expectedMappingStatus + countryCode.

### Copilot — 2026-02-16 on `src/main/kotlin/nl/teqplay/poma/feature/infrastructure/port/AbstractPortDatasource.kt`

The aggregation groups by MongoDB `_id`, but `MappingStatusCount` defines `status` (not `_id` / `@BsonId`). This will likely deserialize `status` as null for every group, breaking the mapping overview counts. Consider renaming the field to `_id` (like other aggregate result DTOs) or annotating `status` with `@BsonId`, and update consumers accordingly.

### Copilot — 2026-02-16 on `src/main/kotlin/nl/teqplay/poma/model/aggregation/MappingStatusCount.kt`

`MappingStatusCount` uses `status` to hold the Mongo aggregation group key, but Mongo will return that key in `_id` unless you project/rename it. Without using `_id` or `@BsonId`, `status` will deserialize as null and your grouping will not work as intended.
```suggestion
import nl.teqplay.poma.model.basemodels.Port
import org.bson.codecs.pojo.annotations.BsonId

data class MappingStatusCount(
    @BsonId
```

### Copilot — 2026-02-16 on `src/main/kotlin/nl/teqplay/poma/model/basemodels/Port.kt`

The secondary constructor parameter is named `mappingStatus`, but it actually populates the `expectedMappingStatus` property in the primary constructor. Renaming this parameter (and the forwarded argument) to `expectedMappingStatus` would avoid confusion and make call sites clearer.

### Copilot — 2026-02-16 on `src/main/kotlin/nl/teqplay/poma/feature/infrastructure/port/PortService.kt`

This uses the named argument `mappingStatus`, which (via the secondary constructor) maps to `expectedMappingStatus` on `Port`. Consider aligning the constructor parameter name and call site to `expectedMappingStatus` to avoid mis-setting the wrong field later.
```suggestion
            expectedMappingStatus = getMappingStatus(apiModel.expectedMappingStatus),
```

### Copilot — 2026-02-16 on `src/main/kotlin/nl/teqplay/poma/util/InfrastructureUtils.kt`

Local variable is named `source` but represents a `mappingStatus`. Renaming it would improve readability and reduce copy/paste confusion with `getSource`/`getSourceType`.

### Copilot — 2026-02-16 on `src/main/kotlin/nl/teqplay/poma/feature/mapping/MappingService.kt`

`getMappingOverview()` ignores ports whose `expectedMappingStatus` is missing/unknown (aggregation group key will be null). That will make `total` undercount and the page misleading for existing documents created before this field existed. Consider folding `null` into `NOT_MAPPED` (either in the aggregation pipeline via `$ifNull` or in Kotlin when building `counts`).

### Copilot — 2026-02-16 on `src/main/kotlin/nl/teqplay/poma/feature/mapping/MappingService.kt`

`skip` can become negative when `page < 1` (or overflow when very large), and `limit` can be 0/negative, which can lead to Mongo errors or unexpected results. Consider validating `page >= 1` and `limit > 0` (and returning a 400) before calculating `skip`.
